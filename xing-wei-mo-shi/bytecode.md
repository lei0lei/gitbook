# Bytecode

### 意图

把行为编码成虚拟机指令，让行为拥有数据般的灵活性。

### 动机

做游戏或许有趣，但绝不轻松。现代游戏需要巨大、复杂的代码库。主机厂商和应用市场的守门人有严格的质量要求，一个崩溃 bug 就能让游戏无法发售。

我参与过一个有六百万行 C++ 的游戏。对比一下：控制火星好奇号漫游车的软件还不到这个数字的一半。

同时，我们还被要求榨干平台的每一滴性能。游戏对硬件的压榨无人能及，必须不懈优化才能跟上竞争。

为满足高稳定性与高性能，我们求助于 C++ 这类重量级语言：既有低层表达力以充分利用硬件，又有丰富类型系统来预防或至少约束 bug。

我们以此为傲，但这是有代价的。成为熟练程序员需要多年专精训练，之后还要应付代码库的规模。大型游戏的构建时间介于“去喝杯咖啡”和“自己烘焙豆子、手磨、拉意式、打奶泡，还在泡沫上练拉花”之间。

除这些挑战外，游戏还有一个讨厌约束：_好玩_。玩家既要新颖体验，又要精心平衡。这需要不断迭代；可若每次微调都要烦工程师在一堆底层代码里折腾，再等一次冰川般的重编译，创意流就被掐死了。

#### 法术对决！

假设我们在做一款魔法格斗游戏。两个巫师对决，互扔附魔，直到分出胜负。法术可以写在代码里，但那就意味着每次修改都要工程师参与。设计师想改几个数字、感受一下手感，就得重编译整个游戏、重启，再打一场。

和如今多数游戏一样，发售后也要能更新——修 bug、加内容。若法术全硬编码，更新就意味着给可执行文件打补丁。

再进一步：我们还想支持 _mod_。希&#x671B;_&#x7528;&#x6237;_&#x80FD;自创法术。若写在代码里，每个 mod 作者都要完整编译工具链，还得开放源码。更糟的是，法术有 bug 可能让别的玩家机器上的游戏崩溃。

#### 数据 > 代码

很明显，引擎的实现语言并不合适。法术需要与核心游戏安全隔离；要易改、易热加载，并与可执行文件物理分离。

不知你怎么看，在我看来这很&#x50CF;_&#x6570;据_。若能把行为定义在独立数据文件里，由引擎加载并以某种方式“执行”，目标就能达成。

只是要弄清对数据而言“执行”意味着什么：文件里的字节如何表达行为？有几种做法。对比另一种模式——[解释器（Interpreter）](http://en.wikipedia.org/wiki/Interpreter_pattern)——有助于看&#x6E05;_&#x672C;_&#x6A21;式的优劣。

#### 解释器模式

这个模式我本可写一整章，但另有四位老兄已经写过了。这里只塞进最短介绍。

起点是一门你想执行的语言——想&#x60F3;_&#x7F16;&#x7A0B;_&#x8BED;言。例如支持这样的算术表达式：

```
// Some code
(1 + 2) * (3 - 4)
```

然后把表达式的每一块、语言语法的每条规则，都变成一&#x4E2A;_&#x5BF9;象_。数字字面量是对象（基本上是包着原始值的小包装）；运算符也是对象，并持有对操作数的引用。考虑括号与优先级后，表达式就神奇地变成一棵对象小树。

这“魔法”是什么？很简单——_解析_。解析器把字符串变&#x6210;_&#x62BD;象语法树_：一堆表示文本语法结构的对象。

搞出一棵这样的树，你就有了半个编译器。

解释器模式不关&#x5FC3;_&#x521B;&#x5EFA;_&#x90A3;棵树，而关&#x5FC3;_&#x6267;&#x884C;_&#x5B83;。做法很巧：树中每个对象是一个表达式或子表达式。真正面向对象地，我们让表达式自己求值。

先定义所有表达式实现的基接口：

```
// Some code
class Expression
{
public:
  virtual ~Expression() {}
  virtual double evaluate() = 0;
};
```

再为语法中每种表达式定义实现类。最简单的是数字：

```
// Some code
class NumberExpression : public Expression
{
public:
  NumberExpression(double value)
  : value_(value)
  {}

  virtual double evaluate()
  {
    return value_;
  }

private:
  double value_;
};
```

字面量数字表达式求值就是返回自身值。加法与乘法更复杂，因为含有子表达式；求值前要递归求值子表达式：

```
// Some code
class AdditionExpression : public Expression
{
public:
  AdditionExpression(Expression* left, Expression* right)
  : left_(left),
    right_(right)
  {}

  virtual double evaluate()
  {
    // 求值操作数
    double left = left_->evaluate();
    double right = right_->evaluate();

    // 相加
    return left + right;
  }

private:
  Expression* left_;
  Expression* right_;
};
```

乘法的实现想必你能猜到。挺漂亮对吧？几个简单类，就能表示并求值任意复杂的算术表达式。只需创建正确对象并正确连接。

Ruby 大约用这种方式实现了 15 年。到 1.9 版才换成了本章说的字节码。看看我给你省了多少时间！

模式优美简单，但有问题。看图：许多小盒子，许多箭头。代码表现为蔓延的分形小对象树，带来不快后果：

* 从磁盘加载要实例化并连接海量小对象。
* 对象与指针占大量内存。32 位机上，上面那个小算术表达式至少 68 字节（不含填充；若你在家跟做，别忘了虚表指针）。
* 沿指针进入子表达式会屠杀数据缓存；大量虚调用又蹂躏指令缓存。

> 关于缓存及其对性能的影响，见 [Data Locality](https://gameprogrammingpatterns.com/data-locality.html) 一章。

合起来拼写什么？S-L-O-W。广泛使用的语言大多不以解释器模式为基础，就是因为太慢、太吃内存。

#### 机器码，虚拟地

想想我们的游戏。运行时玩家电脑并不会遍历一堆 C++ 语法树结构。我们提前编译成机器码，由 CPU 执行。机器码有什么优势？

* _稠密。_ 是一整块连续二进制数据，没有浪费的位。
* _线性。_ 指令挤在一起，一个接一个执行。除非真有控制流，不会在内存里乱跳。
* _低层。_ 每条指令做相对最小的事，有趣行为来&#x81EA;_&#x7EC4;合_。
* _快。_ 上述特性（加上直接由硬件实现）让机器码疾如风。

听起来棒，但我们不要真正的机器码做法术。让用户提供机器码再由游戏执行，是在求安全问题。我们需要机器码性能与解释器模式安全性之间的折中。

若不加载真正机器码直接执行，而是定义自己&#x7684;_&#x865A;&#x62DF;_&#x673A;器码呢？再在游戏里写一个小模拟器。它类似机器码——稠密、线性、相对低层——又完全由游戏掌控，可以安全沙箱化。

> 这也是许多游戏主机和 iOS 不允许执行运行时加载或生成的机器码的原因。可惜，因为最快的语言实现恰恰这么做：内含“即时编译器”（JIT），把语言即时翻译成优化机器码。

我们称这个小模拟器&#x4E3A;_&#x865A;拟机_（VM），它运行的合成二进制机器码&#x4E3A;_&#x5B57;节码_。它有在数据中定义事物的灵活与易用，性能又好于解释器模式这类更高层表示。

> 在编程语言圈，“虚拟机”与“解释器”同义，我这里混用。提到 Gang of Four 的解释器模式时，我会加“模式”以示区分。

听起来吓人。本章余下的目标是说明：若把功能列表砍短，其实相当可接近。即便你最终不用这模式，至少能更好理解 Lua 及许多用它实现的语言。

### 模式

指令集定义可执行的低层操作。一系列指令被编码为字节序列。虚拟机一次执行一条指令，并用栈存放中间值。通过组合指令，可定义复杂高层行为。

### 何时使用

这是本书最复杂的模式，别轻易扔进游戏。在你需要定义大量行为，且游戏实现语言不合适时使用，原因包括：

* 太低层，编程繁琐或易错。
* 编译慢或工具问题导致迭代太久。
* 信任太多。若要确保所定义行为不会搞坏游戏，需与其余代码库沙箱隔离。

当然，这列表描述了游戏的很大一块——谁不想更快迭代、更安全？但并非免费。字节码比本地代码慢，不适合引擎性能关键路径。

### 需要注意

创造自己的语言或“系统中的系统”很有诱惑力。这里做最小示例，但现实中这些东西往往会像藤蔓一样疯长。

对我来说，游戏开发同样有诱惑：都是想造一个让别人玩耍、创作的虚拟空间。

每次有人定义小语言或脚本系统，都会说“别担心，会很小。”然后不可避免地加功能，直到变成完整语言。

只是，与其他语言不同，它是临时、有机长出来的，架构优雅度约等于棚户区。

> 例如，见每一个模板语言。

当然，做完整语言没什么错——只要有意为之。否则要严格控制字节码能表达的范围。给它套短绳，别让它跑丢。

#### 你需要前端

低层字节码指令利于性能，但二进制字节码格&#x5F0F;_&#x4E0D;&#x662F;_&#x7528;户会手写的东西。把行为从代码挪出，是为了&#x7528;_&#x66F4;&#x9AD8;_&#x5C42;表达。若 C++ 太低层，让用户写汇编——哪怕是你自己设计的——也不是改进！

> 挑战这一断言的是经典游戏 [RoboWar](http://en.wikipedia.org/wiki/RoboWar)：玩家用极似汇编的语言写小程序控制机器人，正是我们这里讨论的指令集风格。那是我第一次接触类汇编语言。

与解释器模式一样，假定你还有某种方&#x5F0F;_&#x751F;&#x6210;_&#x5B57;节码。通常用户用更高层格式编写行为，工具再翻译成 VM 理解的字节码。换句话说：编译器。

我知道这吓人，所以在此提出：若没有资源做创作工具，字节码就不适合你。但后面会看到，也许没你想的那么糟。

#### 你会怀念调试器

编程很难。我们知道想让机器做什么，但不总能正确传达——于是写 bug。为找修，我们堆了一堆工具：调试器、静态分析、反编译器等。这些工具都面向已有语言：机器码或更高层语言。

定义自己的字节码 VM 后，这些工具就甩在身后了。你可以在调试器里单步 VM，但那只告诉你 V&#x4D;_&#x672C;&#x8EAB;_&#x5728;做什么，而不是它解释的字节码在干什么，更无法把字节码映射回编译前的高层形式。

若定义的行为简单，或许能凑合。但内容规模增大时，要计划投入真实时间，帮用户看清字节码在做什么。这些功能或许不会随游戏发售，但对&#x4F60;_&#x80FD;&#x5426;_&#x771F;正发售至关重要。

当然，若游戏要可 mod，这些功&#x80FD;_&#x4F1A;_&#x53D1;售，且更重要。

### 示例代码

看完前几节，实现之直白或许会让你吃惊。先为 VM 设计指令集。在想字节码之类之前，先把它当成 API。

#### 魔法 API

若法术用纯 C++，需要什么样的 API 让这些代码回调引擎？法术基于哪些引擎基本操作？

多数法术最终改变巫师的某项属性，先来几个：

```
// Some code
void setHealth(int wizard, int amount);
void setWisdom(int wizard, int amount);
void setAgility(int wizard, int amount);
```

第一个参数标明影响哪个巫师，比如 `0` 是玩家、`1` 是对手。这样治疗可作用于己方，伤害攻击可作用于宿敌。这三个小方法已覆盖出奇多种魔法效果。

若法术只默默改属性，逻辑没问题，但玩起来会无聊到哭。修一下：

```
// Some code
void playSound(int soundId);
void spawnParticles(int particleType);
```

这些不影响玩法，但拉高&#x4E86;_&#x4F53;&#x9A8C;_&#x5F3A;度。还可加镜头震动、动画等，这些够起步。

#### 魔法指令集

再看如何把&#x8FD9;_&#x7A0B;序化_ API 变成可由数据控制的东西。从小处开始，再推到全貌。先丢掉所有参数。假定 `set___()` 总影响玩家自己的巫师，且总把属性拉满；特效总播一个硬编码音效和粒子。

如此，法术只是一系列指令。每条标明要执行哪项操作。可枚举：

```
// Some code
enum Instruction
{
  INST_SET_HEALTH      = 0x00,
  INST_SET_WISDOM      = 0x01,
  INST_SET_AGILITY     = 0x02,
  INST_PLAY_SOUND      = 0x03,
  INST_SPAWN_PARTICLES = 0x04
};
```

在数据中编码法术，就是存一组 `enum` 值。原语很少，`enum` 范围轻松塞进一个字节。于是法术代码就是一列字节——因此叫“字节码”。

有些字节码 VM 每条指令不止一字节，解码规则更复杂。x86 等常见芯片上的真机器码要复杂得多。

但单字节对 [Java 虚拟机](http://en.wikipedia.org/wiki/Java_virtual_machine) 和构成 .NET 骨干的 Microsoft [CLR](http://en.wikipedia.org/wiki/Common_Language_Runtime) 已经够用，对我们也够。

执行单条指令：看是哪个原语，分派到对应 API：

```
// Some code
switch (instruction)
{
  case INST_SET_HEALTH:
    setHealth(0, 100);
    break;

  case INST_SET_WISDOM:
    setWisdom(0, 100);
    break;

  case INST_SET_AGILITY:
    setAgility(0, 100);
    break;

  case INST_PLAY_SOUND:
    playSound(SOUND_BANG);
    break;

  case INST_SPAWN_PARTICLES:
    spawnParticles(PARTICLE_FLAME);
    break;
}
```

这样，解释器就成了代码世界与数据世界的桥。可包进小 VM，执行整段法术：

```
// Some code
class VM
{
public:
  void interpret(char bytecode[], int size)
  {
    for (int i = 0; i < size; i++)
    {
      char instruction = bytecode[i];
      switch (instruction)
      {
        // 各指令的 case……
      }
    }
  }
};
```

敲进去，你就写了第一个虚拟机。可惜不够灵活：不能定义影响对手或降低属性的法术，只能播一种声音！

要开始有真正语言的表达感，必须引入参数。

#### 栈机

执行复杂嵌套表达式时，从最内层子表达式开始，算出结果向外流，成为外层表达式的参数，直到整个表达式求完。

解释器模式用嵌套对象树显式建模，我们却想要扁平指令列表的速度。仍须保证子表达式结果流到正确的外层表达式。数据已扁平，就要用指&#x4EE4;_&#x987A;&#x5E8F;_&#x63A7;制——做法与 CPU 一样：用栈。

这种架构被毫无想象力地称为[_栈机_](http://en.wikipedia.org/wiki/Stack_machine)。[Forth](http://en.wikipedia.org/wiki/Forth_\(programming_language\))、[PostScript](http://en.wikipedia.org/wiki/PostScript)、[Factor](http://en.wikipedia.org/wiki/Factor_\(programming_language\)) 等语言直接把该模型暴露给用户。

```
// Some code
class VM
{
public:
  VM()
  : stackSize_(0)
  {}

  // 其他……

private:
  static const int MAX_STACK = 128;
  int stackSize_;
  int stack_[MAX_STACK];
};
```

VM 维护内部值栈。本例指令只处理数字，可用简单 `int` 数组。数据要从一条指令传到另一条，就经栈走。

顾名思义，值可压栈或出栈，加两个方法：

```
// Some code
class VM
{
private:
  void push(int value)
  {
    // 检查栈溢出
    assert(stackSize_ < MAX_STACK);
    stack_[stackSize_++] = value;
  }

  int pop()
  {
    // 确保栈非空
    assert(stackSize_ > 0);
    return stack_[--stackSize_];
  }

  // 其他……
};
```

指令需要参数时从栈弹出：

```
// Some code
switch (instruction)
{
  case INST_SET_HEALTH:
  {
    int amount = pop();
    int wizard = pop();
    setHealth(wizard, amount);
    break;
  }

  case INST_SET_WISDOM:
  case INST_SET_AGILITY:
    // 同上……

  case INST_PLAY_SOUND:
    playSound(pop());
    break;

  case INST_SPAWN_PARTICLES:
    spawnParticles(pop());
    break;
}
```

要把&#x503C;_&#x653E;&#x4E0A;_&#x6808;，还需要一条指令：字面量。它表示原始整数。可它自己的值从哪来？如何避免无穷回溯？

技巧是利用指令流是字节序列——可把数字直接塞进字节数组。再定义一种数字字面量指令：

```
// Some code
case INST_LITERAL:
{
  // 从字节码读下一字节
  int value = bytecode[++i];
  push(value);
  break;
}
```

这里为避免多字节整数解码的琐碎代码，只读单字节；真实实现要支持覆盖完整数值范围的字面量。

它把字节码流&#x4E2D;_&#x4E0B;一字节当作数&#x5B57;_&#x8BFB;出并压栈。

串几条指令，看解释器如何执行，感受栈的工作。从空栈、解释器指向第一条指令开始：

1. 执行第一条 `INST_LITERAL`：读下一字节（`0`）压栈。
2. 执行第二条 `INST_LITERAL`：读 `10` 压栈。
3. 执行 `INST_SET_HEALTH`：弹出 `10` 存入 `amount`，弹出 `0` 存入 `wizard`，再以这些参数调用 `setHealth()`。

搞定！我们有了把玩家巫师生命设为 10 点的法术。现在足以定义把任一巫师属性设为任意值的法术，也能播不同音效、生成粒子。

但……这仍&#x50CF;_&#x6570;&#x636E;_&#x683C;式。例如，我们还不能按智慧的一半提升生命。设计师要能表达法术&#x7684;_&#x89C4;则_，而不只&#x662F;_&#x6570;值_。

#### 行为 = 组合

若把小 VM 当成编程语言，目前只支持几个内置函数和常量参数。要让字节码感觉&#x50CF;_&#x884C;为_，缺的&#x662F;_&#x7EC4;合_。

设计师需能创建以有趣方式组合不同值的表达式。简单例子：希望法&#x672F;_&#x589E;&#x51CF;_&#x67D0;量，而&#x975E;_&#x8BBE;&#x6210;_&#x67D0;量。

这需要考虑属性当前值。已&#x6709;_&#x5199;_&#x5C5E;性的指令，还要&#x52A0;_&#x8BFB;_：

```
// Some code
case INST_GET_HEALTH:
{
  int wizard = pop();
  push(getHealth(wizard));
  break;
}

case INST_GET_WISDOM:
case INST_GET_AGILITY:
  // 你懂的……
```

可见它们双向使用栈：弹出参数决定取哪个巫师的属性，再查值压回栈。

这让我们能写在属性间复制的法术：敏捷设为智慧，或把一巫师生命镜像成对手的。

更好，但仍很有限。接下来需要算术。是时候让婴儿 VM 学会 1+1 了。再加几条指令。你大概已摸到门道，只展示加法：

```
// Some code
case INST_ADD:
{
  int b = pop();
  int a = pop();
  push(a + b);
  break;
}
```

像其他指令一样：弹出几个值，做点工作，再把结果压回。此前每条新指令只带来渐进表达力提升；这一步是大跃进。不明显，但我们已能处理各种复杂、深层嵌套的算术表达式。

走一个稍复杂例子：法术把玩家巫师生命增加为其敏捷与智慧的平均值。代码里是：

```
// Some code
setHealth(0, getHealth(0) +
    (getAgility(0) + getWisdom(0)) / 2);
```

你或许以为需要指令处理表达式里括号的显式分组，但栈隐式支持。手工求值步骤：

1. 取巫师当前生命并记住。
2. 取敏捷并记住。
3. 对智慧同样。
4. 取后两个相加，记住结果。
5. 除以二，记住结果。
6. 取出巫师生命，加上该结果。
7. 用该结果设置巫师生命。

看到那些“记住”和“取出”了吗？每个“记住”对应压栈，“取出”对应弹出。因此很容易译成字节码。例如取当前生命：

```
// Some code
LITERAL 0
GET_HEALTH
```

这段把巫师生命压栈。机械翻译每一行，就得到求值原表达式的字节码块。下面演示指令如何组合。

假设当前属性为生命 45、敏捷 7、智慧 11。每条指令旁是执行后的栈，以及用途注释：

```
// Some code
LITERAL 0        [0]             # 巫师索引
LITERAL 0        [0, 0]          # 巫师索引
GET_HEALTH       [0, 45]         # getHealth()
LITERAL 0        [0, 45, 0]      # 巫师索引
GET_AGILITY      [0, 45, 7]      # getAgility()
LITERAL 0        [0, 45, 7, 0]   # 巫师索引
GET_WISDOM       [0, 45, 7, 11]  # getWisdom()
ADD              [0, 45, 18]     # 敏捷 + 智慧
LITERAL 2        [0, 45, 18, 2]  # 除数
DIVIDE           [0, 45, 9]      # 平均敏捷与智慧
ADD              [0, 54]         # 加上当前生命
SET_HEALTH       []              # 设为结果
```

逐步看栈，数据几乎像魔法一样流过。开头压入的巫师索引 `0` 一直挂在栈底，直到最后 `SET_HEALTH` 才用到。

#### 虚拟机

我可以继续加指令，但这里是好停点。我们已经有了不错的小 VM：用简单紧凑的数据格式定义相当开放的行为。“字节码”和“虚拟机”听起来吓人，其实往往只是栈、循环和 switch。

回想最初目标：行为要好好沙箱化。看完 VM 实现，显然做到了。字节码无法恶意行事或伸到引擎奇怪角落，因为我们只定义了少数触及游戏其余部分的指令。

通过栈大小控制内存用量，并小心不让溢出。甚至可控&#x5236;_&#x65F6;间_：在指令循环里跟踪执行条数，超限就退出。

本示例不必控制执行时间，因为没有循环指令。也可通过限制字节码总大小限制时间。这也意味着我们的字节码不是图灵完备的。

只剩一个问题：真&#x6B63;_&#x521B;&#x5EFA;_&#x5B57;节码。迄今我们是手写伪代码再手编成字节码。除非&#x4F60;_&#x5F88;_&#x95F2;，实践中行不通。

#### 施法工具

最初目标之一是&#x7528;_&#x66F4;&#x9AD8;_&#x5C42;方式创作行为，结果却造了比 C++ _更&#x4F4E;_&#x5C42;的东西。运行时性能与安全我们有了，设计师友好的可用性一点没有。

要填这个缺口，需要工具：让用户定义法术的高层行为，再生成对应的低层栈机字节码。

这听起来比做 VM 难多了。许多程序员上过编译原理课，唯一带走的是看到封面有龙的书或 “[lex](http://en.wikipedia.org/wiki/Lex_\(software\))”“[yacc](http://en.wikipedia.org/wiki/Yacc)”就触发的 PTSD。

> 说的当然是经典教材 [_Compilers: Principles, Techniques, and Tools_](https://en.wikipedia.org/wiki/Compilers:_Principles,_Techniques,_and_Tools)。

其实编译基于文本的语言没那么糟，只是话题太广塞不进这里。但你不必那样做。我说需要的&#x662F;_&#x5DE5;具_——输入格式不必&#x662F;_&#x6587;本文&#x4EF6;_&#x7684;_编译器_。

相反，我鼓励考虑做图形界面让用户定义行为，尤其当使用者不太技术时。写出无语法错误的文本，对没被编译器吼过多年的人很难。

你可以做个应用，让用户通过点击拖拽小盒子、下拉菜单等来“脚本”——只要对你想让他们创造的行为有意义。

> 我为 [Henry Hatsworth in the Puzzling Adventure](http://en.wikipedia.org/wiki/Henry_Hatsworth_in_the_Puzzling_Adventure) 写的脚本系统就是这样。

好处是 UI 可让用户无法创建“无效”程序。不必对他们吐错误信息，可主动禁用按钮或提供默认值，确保任意时刻创建物都有效。

我想强调错误处理有多重要。作为程序员，我们常把人为错误当成可耻人格缺陷，力求消灭。

要做用户喜欢的系统，必须拥抱他们的人性，_包括易错性_。犯错是人之常情，也是创作过程的根本部分。用撤销等功能优雅处理错误，能帮用户更有创造力、产出更好内容。

这让你免于为小语言设计语法、写解析器。但有些人觉得 UI 编程同样讨厌——那我就没什么好消息了。

归根结底，本模式关乎以用户友好的高层方式表达行为。你必须打磨用户体验。为高效执行，再译成低层形式。这是真活，但若愿意接受挑战，回报可观。

我尽量让本章保持简单，但我们实际在创造一门语言。设计空间相当开放。探索可以很有趣——别忘了把游戏做完。

#### 指令如何访问栈？

字节码 VM 主要有两种口味：基于栈与基于寄存器。栈式 VM 中，指令总从栈顶工作，如示例。例如 `INST_ADD` 弹出两值相加再压回结果。

寄存器式 VM 仍有栈。差别是指令可从栈更深位置读输入。`INST_ADD` 不再&#x603B;_&#x5F39;&#x51FA;_&#x64CD;作数，而是在字节码里存两个索引，标明从栈何处读操作数。

* 栈式 VM：
  * _指令小。_ 参数隐式在栈顶，无需编码，指令通常单字节。
  * _代码生成更简单。_ 写输出字节码的编译器/工具时，生成栈式字节码更简单：只要按正确顺序输出指令，即可在其间传参。
  * _指令更多。_ 每条指令只看见栈顶。像 `a = b + c` 需要多条指令把 `b`、`c` 移到栈顶、运算，再把结果移入 `a`。
* 寄存器式 VM：
  *   _指令更大。_ 需要栈偏移参数，位数更多。例如 Lua——大概最知名的寄存器式 VM——指令整整 32 位：6 位指令类型，其余是参数。

      > Lua 团队不规定字节码格式，且版本间会变。这里描述的是 Lua 5.1。对 Lua 内部极佳的深潜，可读相关资料。
  * _指令更少。_ 每条能做更多事，不必那么多。有人说性能更好，因为少在栈里倒腾值。

该选哪个？我建议坚持栈式。实现更简单，生成代码也简单得多。寄存器式因 Lua 转为该风格而获“更快”名声，但极依赖你的实际指令及 VM 诸多细节。

#### 有哪些指令？

指令集划定字节码能/不能表达的边界，也大幅影响 VM 性能。可能需要的指令种类清单：

* 外部原语。 伸出 VM 进入引擎其余部分、做用户可见之事。决定字节码能表达何种真实行为。没有它们，VM 只能空转 CPU。
* 内部原语。 在 VM 内操纵值——字面量、算术、比较、倒腾栈等。
* 控制流。 示例未覆盖。若要行为带条件执行或循环多次执行，需要控制流。在字节码低层语言里它们惊人地简单：跳转。\
  指令循环里有索引跟踪当前位置。跳转指令只是改那个变量，改变当前执行位置。换句话说：`goto`。可用它构建各种高层控制流。
* 抽象。 用户在数据里定&#x4E49;_&#x5F88;&#x591A;_&#x4E1C;西后，终会想复用字节码片段，而非复制粘贴。你或许想要可调用过程之类。\
  最简单形式下，过程比跳转复杂不了多少。差别是 VM 维护第二&#x4E2A;_&#x8FD4;&#x56DE;_&#x6808;。执行“call”时把当前指令索引压入返回栈，再跳到被调字节码；遇到“return”则弹出索引跳回。

#### 值如何表示？

示例 VM 只处理一种值：整数。回答很容易——栈就是 `int` 栈。更完整的 VM 会支持字符串、对象、列表等类型。须决定内部如何存储。

* 单一数据类型：
  * _简单。_ 不必担心标记、转换、类型检查。
  * _无法处理不同数据类型。_ 明显短板。把不同类型硬塞进单一表示——比如数字存成字符串——是自找罪受。
* 带标签的变体：\
  动态类型语言的常见表示。每个值有两块：类型标签（`enum`）标明存的是什么类型；其余位按该类型解释：

```
// Some code
enum ValueType
{
  TYPE_INT,
  TYPE_DOUBLE,
  TYPE_STRING
};

struct Value
{
  ValueType type;
  union
  {
    int    intValue;
    double doubleValue;
    char*  stringValue;
  };
};
```

* _值知道自己的类型。_ 可在运行时检查类型——对动态分派、避免对不支持的类型做运算很重要。
* _更占内存。_ 每个值多带几位标明类型；在 VM 这般低层，几位很快积少成多。
* 无标签联合：\
  仍用 union，&#x4F46;_&#x6CA1;&#x6709;_&#x7C7B;型标签。一小撮位可表示多种类型，由你确保不误解释。\
  这是静态类型语言在内存中的表示方式。类型系统在编译期保证你不误解释，运行时不必验证。\
  也是汇编、Forth &#x7B49;_&#x65E0;类&#x578B;_&#x8BED;言存值的方式——留&#x7ED9;_&#x7528;&#x6237;_&#x786E;保不写错解释类型的代码。非胆大者勿入！
  * _紧凑。_ 只存值本身所需位，不能更高效了。
  * _快。_ 无类型标签意味着也不花周期运行时检查。静态类型语言往往比动态快的原因之一。
  * _不安全。_ 真正代价。坏字节码把数字当指针（或反过来）可破坏游戏安全或导致崩溃。\
    若字节码由静态类型语言编译，你或许觉得安全——编译器不会生成不安全字节码。也许对，但记住恶意用户可手搓邪恶字节码、绕过你的编译器。\
    因此例如 JVM 加载程序时必须&#x505A;_&#x5B57;节码验证_。
* 接口：\
  面向对象对“可能是多种类型之一”的解法是多态。接口提供各种类型测试与转换的虚方法：

```
// Some code
class Value
{
public:
  virtual ~Value() {}

  virtual ValueType type() = 0;

  virtual int asInt() {
    // 只能对 int 调用
    assert(false);
    return 0;
  }

  // 其他转换方法……
};
```

再为每种具体类型建具体类，如：

```
// Some code
class IntValue : public Value
{
public:
  IntValue(int value)
  : value_(value)
  {}

  virtual ValueType type() { return TYPE_INT; }
  virtual int asInt() { return value_; }

private:
  int value_;
};
```

* _开放。_ 只要实现基接口，可在核心 VM 外定义新值类型。
* _面向对象。_ 若信奉 OOP，这是“正确”做法，用多态分派而非按类型标签 switch。
* _冗长。_ 每种类型都要单独类及仪式性套话。前面例子展示&#x4E86;_&#x5168;&#x90E8;_&#x503C;类型的完整定义；这里只覆盖一种！
* _低效。_ 要多态就得经指针，布尔和数字等小值也要包成堆上对象。每次碰值都要虚调用。\
  在虚拟机核心，这种小性能打击很快累积。实际上，它有许多我们为避开解释器模式而避免的问题，只是问题现在&#x5728;_&#x503C;_&#x4E0A;而&#x975E;_&#x4EE3;&#x7801;_&#x4E0A;。

我的建议：能坚持单一数据类型就坚持。否则用带标签联合。世界上几乎所有语言解释器都这么做。

#### 字节码如何生成？

最重要的问题留到最后。我带你走过&#x4E86;_&#x6D88;&#x8D39;_&#x4E0E;_解&#x91CA;_&#x5B57;节码的代码，&#x4F46;_&#x4EA7;&#x751F;_&#x5B83;靠你。典型方案是写编译器，但不是唯一选项。

* 若定义基于文本的语言：
  * _必须定义语法。_ 业余与专业语言设计者都系统性地低估其难度。让解析器高兴的文法容易；&#x8BA9;_&#x7528;&#x6237;_&#x9AD8;兴的文&#x6CD5;_&#x5F88;难_。语法设计就是 UI 设计，把界面约束成一串字符并不会让过程更容易。
  * _必须实现解析器。_ 尽管名声不佳，这部分相当容易。用 ANTLR、Bison 等生成器，或像我一样手写小递归下降，就够了。
  * _必须处理语法错误。_ 这是过程中最重要也最难的部分之一。用户会不断犯语法与语义错误，你的职责是把他们引回路上。解析器停在意外标点时，给出有用反馈并不容易。
  * _可能吓跑非技术用户。_ 程序员喜欢文本文件，配合强大命令行工具，我们视其为计算的乐高——简单却能以百万种方式组合。多数非程序员不这么看：对他们来说，文本文件像在给愤怒的机器人审计员填税表，漏一个分号就会被吼。
* 若定义图形化创作工具：
  * _必须实现用户界面。_ 按钮、点击、拖拽之类。有人对此皱眉，我个人喜欢。走这条路时，要把 UI 设计当核心职责，而非应付了事的讨厌活。这里多做的每一点都会让工具更易用、更愉快，直接带来更好的游戏内容。许多你爱的游戏背后，秘密往往是好玩的创作工具。
  * _错误情况更少。_ 用户一步步交互构建行为，应用可一有苗头就引导远离错误。基于文本的语言要等用户扔来整个文件才看到内容，更难预防与处理错误。
  * _可移植性更难。_ 文本编译器的好处是文本文件通用：读一个文件、写一个文件，跨 OS 移植很琐碎（除了换行和编码）。做 UI 要选框架，许多绑定单一 OS。也有跨平台 UI 工具包，但往往以熟悉感换普及——在所有平台上都同样陌生。
