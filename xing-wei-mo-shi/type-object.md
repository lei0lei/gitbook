# Type Object

### 意图

通过创建一个类——其实例各自代表一种不同的对象类型——从而灵活地创建新的“类”。

### 动机

假设我们在做奇幻角色扮演游戏。任务是为要屠宰英勇英雄的成群恶怪写代码。

怪物有许多属性：生命、攻击、图形、声音等，但举例我们只关心前两项。

游戏中每个怪物都有当前生命值：开始时满血，受伤就减少。怪物还有攻击字符串：攻击英雄时，该文本会以某种方式展示给用户（这里不关心怎么展示）。

设计师告诉我们，怪物分多&#x79CD;_&#x54C1;种_（breed），如“龙”或“巨魔”。每个品种描述游戏中存在的一种怪物；同时可有多个同品种怪物在地牢里活动。

品种决定怪物的初始生命——龙比巨魔更高，更难杀。也决定攻击字符串——同品种怪物攻击方式相同。

#### 典型 OOP 答案

带着这套设计打开编辑器开写。按设计，龙是一种怪物，巨魔是另一种，其余品种同理。按面向对象思维，这导向一个 `Monster` 基类：

> 这就是所谓的“是一个”（is-a）关系。传统 OOP 里，因为龙“是一个”怪物，我们就让 `Dragon` 成为 `Monster` 的子类。后面会看到，子类化只是把这类概念关系写进代码的一种方式。
>
>

```
// Some code
class Monster
{
public:
  virtual ~Monster() {}
  virtual const char* getAttack() = 0;

protected:
  Monster(int startingHealth)
  : health_(startingHealth)
  {}

private:
  int health_; // 当前生命
};
```

公有 `getAttack()` 让战斗代码在怪物攻击英雄时拿到要显示的字符串。每个派生品种类会重写它，给出不同消息。

构造函数是 protected，接收怪物初始生命。我们会为每个品种做派生类，提供各自公有构造函数，调用这个并传入该品种合适的初始生命。

再看几个品种子类：

```
// Some code
class Dragon : public Monster
{
public:
  Dragon() : Monster(230) {}

  virtual const char* getAttack()
  {
    return "The dragon breathes fire!";
  }
};

class Troll : public Monster
{
public:
  Troll() : Monster(48) {}

  virtual const char* getAttack()
  {
    return "The troll clubs you!";
  }
};
```

> 感叹号让一切更激动人心！

每个从 `Monster` 派生的类传入初始生命，并重写 `getAttack()` 返回该品种的攻击字符串。一切如预期：不多久英雄就能四处屠戮各种野兽。我们继续写，不知不觉已有几十个怪物子类，从酸性史莱姆到僵尸山羊。

然后奇怪地，事情开始拖沓。设计师最终想&#x8981;_&#x4E0A;&#x767E;_&#x4E2A;品种，我们发现整天都在写这七行小的子类并重编译。更糟——设计师开始想调已写好的品种。原先高效的一天退化成：

1. 收到设计师邮件：把巨魔生命从 48 改成 52。
2. 检出并改 `Troll.h`。
3. 重编译游戏。
4. 检入改动。
5. 回邮件。
6. 重复。

整天沮丧，因为我们变成了数据猴子。设计师也沮丧，因为调一个简单数字要等很久。我们需要：改品种属性不必每次重编译整个游戏。更好的是，让设计师能创建和调品种，_完&#x5168;_&#x4E0D;用程序员介入。

#### 为类而设的类

很高层次上，我们要解决的问题很简单。游戏里有一堆不同怪物，想在它们间共享某些属性。成群怪物在打英雄，我们想让其中一些用相同攻击文本。我们通过说它们是同一“品种”、由品种决定攻击字符串来定义。

我们决定用继承实现，因为它符合我们对类的直觉。龙是怪物，游戏里每条龙是这个龙“类”的实例。把每个品种定义为抽象基类 `Monster` 的子类、游戏里每个怪物是该派生品种类的实例，就镜像了这一关系。类层次大致如下：

`Monster` 基类，派生子类 `Dragon`、`Troll` 等。

游戏中每个怪物实例属于某个派生怪物类型。品种越多，类层次越大。问题当然就在这：加新品种就意味着加新代码，每个品种都要编成自己的类型。

这能用，但不是唯一选项。也可把架构做成：每个怪&#x7269;_&#x6709;_&#x4E00;个品种。不为每个品种子类化 `Monster`，而是一个 `Monster` 类加一个 `Breed` 类：

`Monster` 对象持有对 `Breed` 对象的引用。

就这些。两个类。注意：完全没有继承。系统中，游戏里每个怪物只是 `Monster` 类的一个实例。`Breed` 类装的是同品种怪物共享的信息：初始生命与攻击字符串。

为把怪物与品种关联，给每个 `Monster` 实例一个指向含该品种信息的 `Breed` 对象的引用。要拿攻击字符串，怪物只需调其品种上的方法。`Breed` 类实质上定义了怪物的“类型”。每个品种实例是代表不同概&#x5FF5;_&#x7C7B;&#x578B;_&#x7684;_对象_，因此模式名叫 Type Object。

这模式特别强的地方在于：现在我们能定义&#x65B0;_&#x7C7B;&#x578B;_&#x7684;事物，而完全不必复杂化代码库。我们实质上把类型系统的一部分从硬编码的类层次提升到了可在运行时定义的数据。

通过用不同值实例化更多 `Breed`，就能创建上百种不同品种。若用配置文件读入的数据来初始化品种，就能完全用数据定义新怪物类型。简单到设计师都能做！

### 模式

定义一个类型对象类和一个带类型的对象类。每个类型对象实例代表一种不同的逻辑类型。每个带类型的对象存储指向描述其类型的类型对象的引用。

实例特有数据存在带类型对象里；应在同一概念类型的所有实例间共享的数据或行为，存在类型对象里。引用同一类型对象的对象，会像属于同一类型那样工作。这让我们能在一组相似对象间共享数据和行为——很像子类化——但没有固定的硬编码子类集合。

### 何时使用

只要需要定义各种不同“种类”的事物，但把种类烤进语言类型系统太僵硬时，这模式就有用。尤其在下列任一成立时：

* 事先不知道需要哪些类型。（例如：游戏若要支持下载含新怪物品种的内容？）
* 你想修改或添加新类型，不必重编译或改代码。

### 需要注意

本模式把“类型”的定义从命令式却僵硬的代码语言，搬进更灵活但行为更弱的内存中对象世界。灵活是好事，把类型提升到数据也会失去一些东西。

#### 类型对象必须手动跟踪

用 C++ 类型系统之类的东西，一个优势是：编译器自动处理类的簿记。定义每个类的数据自动编进可执行文件的静态内存段，直接能用。

用 Type Object 模式后，我们不但要管理内存中的怪物，还要管理它们&#x7684;_&#x7C7B;型_——必须确保所有品种对象都已实例化，并在怪物需要时一直留在内存。每次创建新怪物，由我们保证它正确初始化了指向有效品种的引用。

我们摆脱了编译器的部分限制，代价是必须自己重做它曾替我们做的事。

> 底层上，C++ 虚方法用“虚函数表”（vtable）实现。vtable 是简单 `struct`，装一组函数指针，类的每个虚方法一个。每个类在内存中有一张 vtable。类的每个实例有一个指向其类 vtable 的指针。\
> 调用虚函数时，代码先查对象的 vtable，再调表中对应函数指针。\
> 听起来耳熟？vtable 就是我们的品种对象；指向 vtable 的指针就是怪物持有的对品种的引用。C++ 类就是把 Type Object 模式应用到 C 上，并由编译器自动处理。

#### 为每种类型定&#x4E49;_&#x884C;&#x4E3A;_&#x66F4;难

用子类化时，可以重写方法并做任何事——过程式算值、调别的代码等。天空是极限。我们甚至可以定义一个按月相改变攻击字符串的怪物子类（狼人应该好用）。

改用 Type Object 后，用成员变量替换重写方法。不再是怪物子类用不&#x540C;_&#x4EE3;码\*\*计&#x7B97;_&#x653B;击字符串，而是品种对象在不&#x540C;_&#x53D8;&#x91CF;_&#x91CC;_&#x5B58;_&#x653B;击字符串。

这使得用类型对象定义类型特&#x6709;_&#x6570;&#x636E;_&#x5F88;容易，定义类型特&#x6709;_&#x884C;&#x4E3A;_&#x5374;很难。例如，若不同品种需要不同 AI 算法，用这模式更有挑战。

绕过限制有几种办法。简单方案：有一套固定的预定义行为，用类型对象里的数&#x636E;_&#x9009;&#x62E9;_&#x5176;中之一。比方说怪物 AI 总是“站着不动”、“追英雄”或“呜咽发抖”（嘿，不可能个个是巨龙）。我们定义函数实现这些行为，再让品种存指向合适函数的指针，把 AI 算法与品种关联。

> 又耳熟了？我们其实是在自己的类型对象里再实现一遍 vtable。

更强方案是真正支持完全用数据定义行为。[Interpreter](http://c2.com/cgi-bin/wiki?InterpreterPattern) 与 [Bytecode](https://gameprogrammingpatterns.com/bytecode.html) 都让我们构建表示行为的对象。读入数据文件并用它创建这些模式之一的数据结构，就把行为定义完全移出代码、进内容。

随着时间推移，游戏越来越数据驱动。硬件更强，限制我们的更多是能创作多少内容，而非能把硬件推多狠。64K 卡带时，挑战是把玩&#x6CD5;_&#x585E;_&#x8FDB;去；双面 DVD 时，挑战是用玩&#x6CD5;_&#x586B;&#x6EE1;_&#x5B83;。

脚本语言及其他更高层定义游戏行为的方式能大幅提升产能，代价是运行时性能次优。硬件持续变好而我们脑力没有，这权衡越来越说得通。

### 示例代码

第一遍实现，从简单入手，搭建动机节描述的基本系统。先从 `Breed` 类开始：

```
// Some code
class Breed
{
public:
  Breed(int health, const char* attack)
  : health_(health),
    attack_(attack)
  {}

  int getHealth() { return health_; }
  const char* getAttack() { return attack_; }

private:
  int health_; // 初始生命
  const char* attack_;
};
```

非常简单：基本是两个数据字段的容器——初始生命与攻击字符串。看怪物如何用它：

```
// Some code
class Monster
{
public:
  Monster(Breed& breed)
  : health_(breed.getHealth()),
    breed_(breed)
  {}

  const char* getAttack()
  {
    return breed_.getAttack();
  }

private:
  int health_; // 当前生命
  Breed& breed_;
};
```

构造怪物时给它一个对品种对象的引用。这就定义了怪物的品种，取代原先用的子类。构造函数里，`Monster` 用品种决定初始生命。拿攻击字符串时，怪物把调用转发给其品种。

这小段代码就是模式的核心。后面都是加成。

#### 让类型对象更像类型：构造函数

目前我们直接构造怪物，并负责传入品种。这和多数 OOP 语言里普通对象的实例化有点反过来——通常不是先分配一块空白内存&#x518D;_&#x7ED9;_&#x5B83;类。而是在类本身上调构造函数，由它负责给我们新实例。

可把同一模式应用到类型对象：

```
// Some code
class Breed
{
public:
  Monster* newMonster() { return new Monster(*this); }

  // 先前的 Breed 代码……
};
```

> “模式”用词没错：我们谈的是 Design Patterns 经典之一：[Factory Method](http://c2.com/cgi/wiki?FactoryMethodPattern)。\
> 有些语言&#x5BF9;_&#x6240;&#x6709;_&#x5BF9;象构造都用这模式。Ruby、Smalltalk、Objective-C 等“类也是对象”的语言里，通过在类对象本身上调方法来构造新实例。

使用它们的类：

```
// Some code
class Monster
{
  friend class Breed;

public:
  const char* getAttack() { return breed_.getAttack(); }

private:
  Monster(Breed& breed)
  : health_(breed.getHealth()),
    breed_(breed)
  {}

  int health_; // 当前生命
  Breed& breed_;
};
```

关键差别是 `Breed` 里的 `newMonster()`——我们的“构造函数”工厂方法。原先实现里，创建怪物像：

> 还有个小差别：示例用 C++，可用便利特性：_友元类_。我们把 `Monster` 构造函数设为私有，阻止任何人直接调用。友元类绕过该限制，让 `Breed` 仍能访问。这意味&#x7740;_&#x552F;&#x4E00;_&#x521B;建怪物的方式是经 `newMonster()`。

```
// Some code
Monster* monster = new Monster(someBreed);
```

改完后变成：

```
// Some code
Monster* monster = someBreed.newMonster();
```

为什么这么做？创建对象有两步：分配与初始化。`Monster` 的构造函数让我们完成所需的一切初始化。本例只是存品种；完整游戏会加载图形、初始化怪物 AI 等。

但那都发生在分&#x914D;_&#x4E4B;后_。构造函数被调用前，我们已经有一块可放怪物的内存。游戏里我们常也想控制对象创建的这一面：通常用自定义分配器或 [Object Pool](https://gameprogrammingpatterns.com/object-pool.html) 等，控制对象落在内存何处。

在 `Breed` 里定义“构造函数”函数，就给了放那类逻辑的地方。`newMonster()` 不必只调 `new`，可先从池或自定义堆取内存，再把控制交给 `Monster` 做初始化。把这逻辑放在 `Breed`、放&#x5728;_&#x552F;&#x4E00;_&#x80FD;创建怪物的函数里，就确保所有怪物都走我们想要的内存管理方案。

#### 通过继承共享数据

目前已是可用的类型对象系统，但很基础。游戏最终会&#x6709;_&#x4E0A;&#x767E;_&#x79CD;不同品种，每种有几十个属性。若设计师想调三十种巨魔、让它们都强一点，就有大量乏味数据录入。

有帮助的是：像品种让多&#x4E2A;_&#x602A;&#x7269;_&#x5171;享属性一样，让多&#x4E2A;_&#x54C1;&#x79CD;_&#x4E5F;能共享属性。与原先 OOP 方案一样，可用继承解决——只是这次不用语言的继承机制，而在类型对象内部自己实现。

为保持简单，只支持单继承。类可有父基类；我们允许品种有父品种：

```
// Some code
class Breed
{
public:
  Breed(Breed* parent, int health, const char* attack)
  : parent_(parent),
    health_(health),
    attack_(attack)
  {}

  int getHealth();
  const char* getAttack();

private:
  Breed* parent_;
  int health_; // 初始生命
  const char* attack_;
};
```

构造品种时给它一个继承的父品种。无祖先的基品种可传 `NULL`。

为真正有用，子品种需控制哪些属性从父继承、哪些自己覆盖指定。本示例系统规定：品种用非零值覆盖生命，用非 `NULL` 字符串覆盖攻击；否则从父继承。

实现方式有两种。一是每次请求属性时动态处理委托：

```
// Some code
int Breed::getHealth()
{
  // 覆盖
  if (health_ != 0 || parent_ == NULL) return health_;

  // 继承
  return parent_->getHealth();
}

const char* Breed::getAttack()
{
  // 覆盖
  if (attack_ != NULL || parent_ == NULL) return attack_;

  // 继承
  return parent_->getAttack();
}
```

优势：运行时若品种改为不再覆盖或不继承某属性，仍正确。另一方面更占内存（要留父指针），也更慢——每次查属性都要走继承链。

若可依赖品种属性不会变，更快方案是&#x5728;_&#x6784;造&#x65F6;_&#x5E94;用继承。这叫“向下复制”（copy-down）委托：创建派生类型时把继承属&#x6027;_&#x5411;下复&#x5236;_&#x8FDB;去：

```
// Some code
Breed(Breed* parent, int health, const char* attack)
: health_(health),
  attack_(attack)
{
  // 继承未覆盖的属性
  if (parent != NULL)
  {
    if (health == 0) health_ = parent->getHealth();
    if (attack == NULL) attack_ = parent->getAttack();
  }
}
```

注意不再需要父品种字段。构造完成后可忘掉父级，属性已复制。访问品种属性只需返回字段：

```
// Some code
int getHealth() { return health_; }
const char* getAttack() { return attack_; }
```

又快又好！

假设引擎通过加载定义品种的 JSON 文件来创建品种，可能像：

```
// Some code
{
  "Troll": {
    "health": 25,
    "attack": "The troll hits you!"
  },
  "Troll Archer": {
    "parent": "Troll",
    "health": 0,
    "attack": "The troll archer fires an arrow!"
  },
  "Troll Wizard": {
    "parent": "Troll",
    "health": 0,
    "attack": "The troll wizard casts a spell on you!"
  }
}
```

我们会有一段代码读每个品种条目，用其数据实例化新品种。从 `"parent": "Troll"` 可见，`Troll Archer` 与 `Troll Wizard` 继承自基品种 `Troll`。

两者生命都是零，因而从基 `Troll` 继承。现在设计师调 `Troll` 的生命，三个品种都会更新。品种数量与每种属性越多，这越能省大量时间。用相当小的代码块，我们就有了一个开放系统，把控制交到设计师手里，并最好地利用他们的时间。

同时，我们可以回去写别的功能。

### 设计决策

Type Object 让我们像在设计自己的编程语言一样构建类型系统。设计空间很开放，可做各种有趣事。

实践中，花俏会被一些因素收束。时间与可维护性会阻止特别复杂的东西。更重要的是：无论设计什么类型对象系统，用户（往往是非程序员）都要能轻松理解。越简单越好用。因此这里覆盖的是已踩过的设计空间，遥远边疆留给学者与探险家。

#### 类型对象是封装还是暴露？

示例实现中，`Monster` 持有对品种的引用，但不公开展示。外部代码无法直接拿到怪物的品种。从代码库视角，怪物实质上无类型，有品种是实现细节。

可轻松改成让 `Monster` 返回其 `Breed`：

```
// Some code
class Monster
{
public:
  Breed& getBreed() { return breed_; }

  // 已有代码……
};
```

> 与书中其他示例一样，我们约定按引用而非指针返回对象，向用户表明永远不会返回 `NULL`。

这改变了 `Monster` 的设计：所有怪物都有品种，成为公有 API 的可见部分。两种选择各有好处。

* 若类型对象被封装：
  * _Type Object 的复杂度对代码库其余部分隐藏。_ 它变成只有带类型对象才需担心的实现细节。
  * _带类型对象可选择性地覆盖类型对象的行为。_ 假设想在怪物濒死时改攻击字符串。攻击字符串总经 `Monster` 访问，就有方便之处插入逻辑：

```
// Some code
const char* Monster::getAttack()
{
  if (health_ < LOW_HEALTH)
  {
    return "The monster flails weakly.";
  }

  return breed_.getAttack();
}
```

若外部直接对品种调 `getAttack()`，我们就没机会插入这逻辑。

* _类型对象暴露的一切都要写转发方法。_ 这是该设计的乏味处。类型对象类方法很多时，对象类要对每个想公开可见的方法再写一套。
* 若类型对象被暴露：
  * _外部代码不需要带类型类的实例也能与类型对象交互。_ 若类型对象被封装，没有包住它的带类型对象就无法使用。这会阻止例如“经品种上方法创建新怪物”的构造模式——用户不能直接拿到品种，就调不了。
  * _类型对象成为对象公有 API 的一部分。_ 一般窄接口比宽接口更易维护——对代码库其余部分暴露越少，复杂度和维护越少。暴露类型对象会把对象 API 拓宽到包含类型对象提供的一切。

#### 带类型对象如何创建？

用这模式后，每个“对象”现在是一对：主对象与它使用的类型对象。二者如何创建并绑定？

* 构造对象并传入其类型对象：
  * _外部代码可控制分配。_ 调用方自己构造两个对象，就能控制发生在内存何处。若希望对象可用于多种内存场景（不同分配器、栈上等），这就给了灵活性。
* 在类型对象上调“构造函数”：
  * _类型对象控制内存分配。_ 硬币另一面。&#x82E5;_&#x4E0D;_&#x60F3;让用户选择对象在内存何处创建，要求他们经类型对象上的工厂方法，就让我们控制分配。若想确保所有对象来自某 [object pool](https://gameprogrammingpatterns.com/object-pool.html) 或其他分配器，这会有用。

#### 类型能否改变？

迄今我们假定对象一旦创建并绑定类型对象，绑定永不改变。生于何种类型，死于何种类型。这并非绝对必须。我&#x4EEC;_&#x53EF;&#x4EE5;_&#x5141;许对象随时间改变类型。

回到例子。设计师说怪物死了有时想让尸体变成复活僵尸。可在怪物死时用僵尸品种生成新怪物；另一选择是拿现有怪物，把它的品种改成僵尸。

* 若类型不变：
  * _编码与理解都更简单。_ 概念上，“类型”多半是人们不指望会变的东西。这固化该假设。
  * _更易调试。_ 若要追查怪物进了奇怪状态的 bug，能假&#x5B9A;_&#x73B0;&#x5728;_&#x770B;的品种就是它一直以来的品种，会简化工作。
* 若类型可变：
  * _更少对象创建。_ 本例中若类型不能变，就得烧周期创建新僵尸怪物、从原怪物复制需保留的属性，再删除它。能改类型的话，全部变成一次简单赋值。
  * _必须小心假设是否满足。_ 对象与其类型之间耦合相当紧。例如，品种可能假定怪&#x7269;_&#x5F53;&#x524D;_&#x751F;命从不高于品种带来的初始生命。\
    若允许改品种，须确保现有对象满足新类型要求。改类型时，多半要跑一些校验代码，确保对象对新类型有意义。

#### 支持何种继承？

* 无继承：
  * _简单。_ 往往最简单的最好。若类型对象间没有大量需要共享的数据，何必为难自己？
  * _可能导致重复劳动。_ 我还未见过设计&#x5E08;_&#x4E0D;&#x60F3;_&#x8981;某种继承的创作系统。有五十种不同精灵时，要在五十个地方改同一个数字来调生命，_糟透了_。
* 单继承：
  * _仍相对简单。_ 易实现，更重要的是也相当好懂。非技术人员要用系统时，活动部件越少越好。许多编程语言只支持单继承是有原因的：似乎是在能力与简单之间的甜点。
  * _查属性更慢。_ 从类型对象取某数据，可能要沿继承链上溯找最终决定该值的类型。若在性能关键代码里，或许不愿花这时间。
* 多重继承：
  * _几乎所有数据重复都可避免。_ 好的多重继承系统能让用户建出几乎无冗余的类型对象层次。调数字时，可避免大量复制粘贴。
  * _复杂。_ 可惜收益似乎更多是理论的而非实践的。多重继承难理解、难推理。\
    若 Zombie Dragon 类型既继承 Zombie 又继承 Dragon，哪些属性来自 Zombie、哪些来自 Dragon？要使用系统，用户须理解继承图如何遍历，并有先见之明设计智能层次。\
    我见到的多数 C++ 编码规范倾向禁止多重继承，Java 与 C# 则完全没有。这是承认一个悲哀事实：做对太难，往往最好干脆不用。值得想想，但很少会想在游戏的类型对象上用多重继承。一如既往：更简单更好。

### 另见

* 本模式高层要解决的问题是在多个对象间共享数据与行为。以另一种方式解决同一问题的是 [Prototype](https://gameprogrammingpatterns.com/prototype.html)。
* Type Object 是 [Flyweight](https://gameprogrammingpatterns.com/flyweight.html) 的近亲。两者都让实例共享数据。Flyweight 意图是省内存，共享数据未必代表任何概念上的对象“类型”；Type Object 焦点在组织与灵活性。
* 本模式与 [State](https://gameprogrammingpatterns.com/state.html) 有很多相似。两者都让对象把定义自身的一部分委托给另一对象。类型对象通常委托对&#x8C61;_&#x662F;_&#x4EC0;么：大致描述对象的不变数据。State 委托对&#x8C61;_&#x6B64;刻&#x662F;_&#x4EC0;么：描述对象当前配置的临时数据。\
  讨论对象改变类型时，可把 Type Object 看成兼任 State。

核心一句话：用 `Breed` 这类运行时对象代替硬编码子类，实例通过引用“类型对象”共享同种数据与行为，新类型可纯数据驱动、无需改编译。
