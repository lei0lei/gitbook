# Singleton

这一章是个例外。本书其他章节都在教你如何使用某种设计模式，而这一章要教你如何不要使用它。

尽管出发点是好的，“四人帮”描述的单例模式通常弊大于利。他们强调这个模式应该谨慎使用，但游戏行业在理解这条信息时，往往把它忽略了。

和任何模式一样，在不合适的地方使用单例模式，就像用夹板治疗枪伤一样有效。由于它被严重滥用，本章大部分内容都会讨论如何避免单例。不过首先，还是让我们了解一下这个模式本身。

当行业中的许多开发者从 C 转向面向对象编程时，他们遇到了一个问题：“我怎样才能获得一个实例？”他们想调用某个方法，却没有提供该方法的对象实例。单例——换句话说，将对象变成全局对象——成了一条简单的出路。

### 单例模式

《设计模式》对单例模式的总结如下：

> 确保一个类只有一个实例，并提供访问该实例的全局入口。

我们从“并”字处将它拆开，分别分析前后两部分。

#### 将一个类限制为单个实例

有些类一旦存在多个实例，就无法正确工作。常见情况是，这个类需要与某个拥有自身全局状态的外部系统交互。

假设有一个类封装了底层文件系统 API。由于文件操作可能需要较长时间才能完成，我们的类会异步执行这些操作。这意味着多个操作可能同时运行，因此必须进行协调。如果一次调用正在创建某个文件，而另一次调用试图删除同一个文件，封装类就必须同时了解这两个操作，确保它们不会相互干扰。

为此，每次对封装类的调用都必须能够访问此前的所有操作。如果用户可以随意创建这个类的实例，那么一个实例就无法知道其他实例启动了哪些操作。

这时，单例模式登场了。它让一个类能够通过自身结构，在编译期确保该类只有一个实例。

#### 提供全局访问入口

游戏中的多个系统都会使用文件系统封装，例如日志记录、内容加载和游戏状态保存。如果这些系统不能创建自己的文件系统实例，又该如何获得那个唯一的实例？

单例模式也为此提供了解决方案。除了创建唯一实例，它还提供了一个全局可用的方法来获取该实例。这样，代码库中的任何地方都可以把爪子伸向这个受到祝福的实例。

经典实现如下：

```cpp
// Some code
class FileSystem
{
public:
  static FileSystem& instance()
  {
    // 延迟初始化。
    if (instance_ == NULL) instance_ = new FileSystem();
    return *instance_;
  }

private:
  FileSystem() {}

  static FileSystem* instance_;
};
```

静态成员 `instance_` 保存该类的实例，私有构造函数确保它是唯一实例。公共静态方法 `instance()` 允许从代码库中的任何位置访问它，并负责在首次有人请求时延迟创建单例实例。

一种现代写法如下：

```cpp
// Some code
class FileSystem
{
public:
  static FileSystem& instance()
  {
    static FileSystem* instance = new FileSystem();
    return *instance;
  }

private:
  FileSystem() {}
};
```

C++11 规定，即使存在并发，局部静态变量的初始化器也只会运行一次。因此，假设你使用的是现代 C++ 编译器，这段代码是线程安全的，而前一个示例不是。

当然，单例类自身是否线程安全则完全是另一个问题！这里只保证它的初始化过程是线程安全的。

### 为什么我们会使用它

看来我们找到了赢家。无须烦琐地到处传递文件系统封装，就能在任何需要它的地方访问它。这个类还巧妙地确保我们不会因为创建多个实例而把事情搞砸。它还有其他几个不错的特性：

* 没有人使用时，它不会创建实例。 节省内存和 CPU 周期总是好事。由于单例只在首次访问时初始化，如果游戏从未请求它，它就永远不会被实例化。
* 它在运行时初始化。 单例的一种常见替代方案是使用包含静态成员变量的类。我喜欢简单的解决方案，因此只要可以，就会使用静态类代替单例。但静态成员有一个限制：自动初始化。

编译器会在调用 `main()` 之前初始化静态变量。这意味着它们不能使用只有程序启动后才能获得的信息，例如从文件中加载的配置。它们也无法可靠地相互依赖，因为编译器不保证不同静态变量之间的初始化顺序。

延迟初始化解决了这两个问题。单例会尽可能晚地初始化，因此到那时，它所需要的信息应该已经可用。只要不存在循环依赖，一个单例甚至可以在初始化自己时引用另一个单例。

* 你可以创建单例的子类。 这是一项强大却经常被忽略的能力。

假设文件系统封装需要支持多个平台。为此，我们希望将其定义为抽象的文件系统接口，并为每个平台创建实现该接口的子类。基类如下：

```cpp
// Some code
class FileSystem
{
public:
  virtual ~FileSystem() {}
  virtual char* readFile(char* path) = 0;
  virtual void  writeFile(char* path, char* contents) = 0;
};
```

然后为几个平台定义派生类：

```cpp
// Some code
class PS3FileSystem : public FileSystem
{
public:
  virtual char* readFile(char* path)
  {
    // 使用 Sony 文件 I/O API……
  }

  virtual void writeFile(char* path, char* contents)
  {
    // 使用 Sony 文件 I/O API……
  }
};

class WiiFileSystem : public FileSystem
{
public:
  virtual char* readFile(char* path)
  {
    // 使用 Nintendo 文件 I/O API……
  }

  virtual void writeFile(char* path, char* contents)
  {
    // 使用 Nintendo 文件 I/O API……
  }
};
```

接下来，将 `FileSystem` 改造成单例：

```cpp
// Some code
class FileSystem
{
public:
  static FileSystem& instance();

  virtual ~FileSystem() {}
  virtual char* readFile(char* path) = 0;
  virtual void  writeFile(char* path, char* contents) = 0;

protected:
  FileSystem() {}
};
```

巧妙之处在于实例的创建方式：

```cpp
// Some code
FileSystem& FileSystem::instance()
{
  #if PLATFORM == PLAYSTATION3
    static FileSystem* instance = new PS3FileSystem();
  #elif PLATFORM == WII
    static FileSystem* instance = new WiiFileSystem();
  #endif

  return *instance;
}
```

只需一个简单的编译器开关，就能将文件系统封装绑定到适当的具体类型。整个代码库都可以通过 `FileSystem::instance()` 访问文件系统，而不会与任何平台专用代码耦合。这种耦合被封装在 `FileSystem` 类自身的实现文件中。

对于这类问题，我们大多数人通常做到这里就会停下。现在已经有了一个可靠工作的文件系统封装，它可以被全局访问，因此任何需要它的地方都能得到它。是时候提交代码，再喝点美味饮料庆祝一下了。

### 为什么我们会后悔使用它

短期来看，单例模式相对无害。和许多设计决策一样，它的代价要到长期才会显现。当我们把几个不必要的单例浇铸成冷冰冰的代码之后，就会买来以下麻烦。

#### 它是一个全局变量

在游戏还是由几个家伙窝在车库里开发的年代，榨干硬件性能比象牙塔里的软件工程原则更加重要。老派的 C 和汇编程序员使用全局变量和静态变量，也照样做出了优秀的游戏。

随着游戏规模和复杂度不断增长，架构和可维护性开始成为瓶颈。我们无法按时发布游戏，不再是因为硬件限制，而是因为生产力限制。

于是，我们转向 C++ 这样的语言，并开始应用软件工程前辈们用惨痛经验换来的智慧。其中一条教训是：全局变量有许多坏处。

**它让代码更难推理**

假设我们正在排查别人编写的某个函数中的缺陷。如果该函数不接触任何全局状态，只需理解函数体和传入的参数，就能掌握它的行为。

计算机科学家将不访问或修改全局状态的函数称为“纯函数”。纯函数更容易推理，也更容易被编译器优化，还能实现记忆化等巧妙技术——缓存并复用函数此前调用的结果。

尽管完全使用纯函数也存在挑战，但它的优点如此诱人，以至于计算机科学家创造了 Haskell 这类只允许纯函数的语言。

现在，想象一下函数中间突然出现了这样的调用：

```cpp
// Some code
SomeClass::getSomeGlobalData()
```

为了弄清楚发生了什么，我们必须搜索整个代码库，查明哪些代码接触了这份全局数据。只有凌晨三点在数百万行代码中执行 `grep`，试图找到那处错误设置静态变量的调用之后，你才会真正痛恨全局状态。

**它鼓励耦合**

团队里的新程序员还不了解游戏那套优美、可维护且低耦合的架构，但他刚刚接到了第一个任务：让巨石撞击地面时播放声音。

你我都知道，绝不能让物理代码与音频这种东西耦合，但他只是想完成任务。不幸的是，`AudioPlayer` 实例是全局可见的。于是，只需添加一条小小的 `#include`，新同事就破坏了我们精心构建的架构。

如果音频播放器没有全局实例，那么即使他包含了头文件，也仍然无法使用它。这种困难会向他传达一个明确的信息：这两个模块不应该相互了解，他必须寻找其他解决方案。

控制对实例的访问，就是控制耦合。

**它对并发不友好**

游戏只运行在简单单核 CPU 上的时代已经基本结束。如今的代码至少必须能够在多线程环境中正常工作，即使它没有充分利用并发。

一旦将某个东西设为全局对象，我们就创建了一块所有线程都能看见和修改的内存，而它们未必知道其他线程正在对其做什么。这条路最终会通向死锁、竞态条件，以及其他如同地狱般难以修复的线程同步缺陷。

这些问题足以让我们远离全局变量，也应该让我们远离单例模式。但这仍然没有告诉我们游戏究竟应该如何设计：没有全局状态时，怎样构建游戏架构？

这个问题有一些非常全面的答案——从某种意义上说，本书的大部分内容都在回答它——但这些答案既不明显，也不容易获得。与此同时，我们仍然必须把游戏做出来。

单例模式看起来像是包治百病的灵药。它出现在一本面向对象设计模式的书中，所以架构上肯定没有问题，对吧？而且，它还允许我们继续使用多年来习惯的软件设计方式。

不幸的是，它与其说是解药，不如说是安慰剂。看看全局变量造成的问题，你会发现单例模式一个都没有解决。因为单例就是全局状态，只不过被封装进了一个类中。

#### 即使你只需要解决一个问题，它也会同时解决两个

“四人帮”对单例模式的描述中，那个“并”字有点奇怪。这个模式究竟是在解决一个问题，还是两个问题？如果我们只面临其中一个问题呢？

确保只有一个实例确实很有用，但谁说我们希望所有人都能随意摆弄它？同样，全局访问确实很方便，但对于允许创建多个实例的类，这一点也依然成立。

在这两个问题中，后者——方便访问——几乎总是我们采用单例模式的真正原因。

以日志类为例。游戏中的大多数模块都可以从记录诊断信息的能力中获益。然而，如果把 `Log` 实例传给每一个函数，不仅会弄乱方法签名，还会分散人们对代码真正意图的注意力。

显而易见的解决方案是将 `Log` 类变成单例。这样，每个函数都可以直接通过这个类获取实例。但这样做时，我们也无意间得到了一条奇怪的限制：突然之间，我们再也无法创建多个日志记录器了。

起初这不是问题。我们只写入一个日志文件，因此本来就只需要一个实例。但到了开发周期后期，麻烦出现了。团队中的每个人都在使用这个日志记录器输出诊断信息，日志文件变成了巨大的垃圾场。程序员必须趟过一页又一页的文本，才能找到自己关心的那条记录。

我们希望将日志拆分到多个文件中，为游戏的不同领域分别创建日志记录器，例如网络、UI、音频和游戏玩法。但我们做不到。

`Log` 类不仅不再允许创建多个实例，这项设计限制还已经深深嵌入了每一个使用它的调用位置：

```cpp
// Some code
Log::instance().write("Some event.");
```

为了让 `Log` 类重新支持多个实例——就像它最初那样——我们必须同时修改类本身，以及所有提到它的代码。原本方便的访问方式，现在不再那么方便了。

情况还可能更糟。假设 `Log` 类属于一个由多个游戏共享的库。现在，要修改它的设计，你必须协调多个团队，而其中大多数人既没有时间，也没有动力配合修复。

#### 延迟初始化剥夺了你的控制权

在拥有虚拟内存、性能要求相对宽松的桌面 PC 世界里，延迟初始化是一项聪明的技巧。但游戏是另一种动物。

初始化系统可能需要耗费时间，例如分配内存、加载资源等。如果初始化音频系统需要几百毫秒，我们就必须控制它在什么时候发生。如果任由音频系统在第一次播放声音时延迟初始化，那一刻可能正处于紧张激烈的游戏场景中，从而造成明显的掉帧和卡顿。

同样，游戏通常需要严密控制堆内存布局，以避免内存碎片。如果音频系统在初始化时从堆中分配一块内存，我们就希望知道初始化何时发生，以便控制这块内存在堆中的位置。

关于内存碎片的详细说明，请参阅“对象池”一章。

正因为这两个问题，我见过的大多数游戏都不依赖延迟初始化，而是像下面这样实现单例模式：

```cpp
// Some code
class FileSystem
{
public:
  static FileSystem& instance() { return instance_; }

private:
  FileSystem() {}

  static FileSystem instance_;
};
```

这解决了延迟初始化问题，却牺牲了单例相对于原始全局变量所拥有的几个优点。

使用静态实例后，我们无法再使用多态，而且该类必须能够在静态初始化阶段构造。我们也无法在不再需要实例时释放它所占用的内存。

我们现在拥有的其实不是单例，而只是一个简单的静态类。这未必是坏事，但如果只需要静态类，为什么不彻底去掉 `instance()` 方法，直接使用静态函数？

调用 `Foo::bar()` 比调用 `Foo::instance().bar()` 更简单，而且能够明确表明你确实是在处理静态内存。

选择单例而不是静态类的常见理由是：如果以后决定把静态类改成非静态类，就必须修改每一个调用位置。理论上，使用单例时不必这样做，因为你可以传递实例，并像普通实例方法那样调用它。

但在实践中，我从未见过这种情况。所有人都只会在一行里写：

```cpp
// Some code
Foo::instance().bar()
```

如果将 `Foo` 改成非单例，仍然必须修改每个调用位置。既然如此，我宁愿使用更简单的类和更简单的调用语法。

### 我们可以改用什么

如果目前为止我已经达成了目标，那么下次遇到问题、准备从工具箱中拿出单例模式时，你应该会三思。

但问题仍然需要解决。你应该拿出哪件工具？具体取决于你想做什么，我有几种方案供你考虑。不过首先……

#### 先看看是否真的需要这个类

我在游戏中看到的许多单例类都是“管理器”——这类含义模糊的类，其存在目的只是照看其他对象。

我见过一些代码库，仿佛每个类都有一个管理器：

* `Monster`、`MonsterManager`
* `Particle`、`ParticleManager`
* `Sound`、`SoundManager`
* `ManagerManager`

为了增加一点变化，他们偶尔还会塞入“系统”或“引擎”，但本质上还是同一个东西。

照管类有时确实有用，但它们通常只是反映出开发者不熟悉面向对象编程。看看下面两个刻意设计的类：

```cpp
// Some code
class Bullet
{
public:
  int getX() const { return x_; }
  int getY() const { return y_; }

  void setX(int x) { x_ = x; }
  void setY(int y) { y_ = y; }

private:
  int x_, y_;
};

class BulletManager
{
public:
  Bullet* create(int x, int y)
  {
    Bullet* bullet = new Bullet();
    bullet->setX(x);
    bullet->setY(y);

    return bullet;
  }

  bool isOnScreen(Bullet& bullet)
  {
    return bullet.getX() >= 0 &&
           bullet.getX() < SCREEN_WIDTH &&
           bullet.getY() >= 0 &&
           bullet.getY() < SCREEN_HEIGHT;
  }

  void move(Bullet& bullet)
  {
    bullet.setX(bullet.getX() + 5);
  }
};
```

这个例子可能有点愚蠢，但我见过许多代码。刮掉表面那些结块的细节之后，露出的设计就是这个样子。

看到这段代码时，很自然会认为 `BulletManager` 应该是单例。毕竟，任何拥有 `Bullet` 的地方都会需要这个管理器，而且你又需要多少个 `BulletManager` 实例呢？

实际上，答案是零。下面是解决这个管理器“单例”问题的方法：

```cpp
// Some code
class Bullet
{
public:
  Bullet(int x, int y) : x_(x), y_(y) {}

  bool isOnScreen()
  {
    return x_ >= 0 && x_ < SCREEN_WIDTH &&
           y_ >= 0 && y_ < SCREEN_HEIGHT;
  }

  void move() { x_ += 5; }

private:
  int x_, y_;
};
```

搞定。没有管理器，也就没有问题。

设计不良的单例通常是一些“辅助类”，它们为另一个类添加功能。如果可以，直接把这些行为移入它所帮助的类。毕竟，面向对象编程的理念就是让对象照顾好自己。

除了管理器，还有其他一些问题也会让我们想到单例。针对这些问题，也有一些替代方案值得考虑。

### 限制一个类只能拥有一个实例

这是单例模式提供的两项能力之一。正如文件系统示例所示，确保某个类只有一个实例可能至关重要。

不过，这不一定意味着我们还希望为该实例提供公开的全局访问。我们可能希望只允许代码中的特定区域访问它，甚至让它成为某个类的私有成员。在这些情况下，提供公开的全局访问入口反而会削弱架构。

例如，我们可能会把文件系统封装隐藏在另一层抽象之后。

我们需要一种既能保证只有一个实例，又不会提供全局访问的方式。实现它有几种办法，下面是其中一种：

```cpp
// Some code
class FileSystem
{
public:
  FileSystem()
  {
    assert(!instantiated_);
    instantiated_ = true;
  }

  ~FileSystem() { instantiated_ = false; }

private:
  static bool instantiated_;
};

bool FileSystem::instantiated_ = false;
```

这个类允许任何人构造它，但如果尝试创建多个实例，就会触发断言并失败。只要正确的代码首先创建了实例，我们就能确保其他代码既无法访问该实例，也无法创建自己的实例。

这个类保证了自己关心的“单一实例”要求，却没有规定应该如何使用它。

断言函数是一种将契约嵌入代码的方式。调用 `assert()` 时，它会计算传入的表达式：

* 如果结果为 `true`，什么也不做，游戏继续运行。
* 如果结果为 `false`，游戏会立即在该位置停止。

在调试版本中，它通常会启动调试器，或者至少打印断言失败所在的文件和行号。

`assert()` 的意思是：“我断言这件事应该永远为真。如果不是，那就是缺陷，我希望程序立刻停下来，以便你修复它。”

这让你可以在不同代码区域之间定义契约。如果某个函数断言其参数之一不为 `NULL`，它表达的就是：“我与调用者之间的契约是：你不能向我传入 `NULL`。”

断言可以帮助我们在游戏刚刚做出意外行为时就发现缺陷，而不是等到错误最终演变成用户可见的问题。它们就像代码库中的围栏，把缺陷圈在产生它们的代码附近，不让它们逃走。

这种实现的缺点是，防止创建多个实例的检查只能在运行时进行。相比之下，单例模式通过类自身的结构，在编译期保证只有一个实例。

### 提供对实例的便捷访问

便捷访问是我们采用单例模式的主要原因。单例让我们能够轻松获得那个会在许多地方使用的对象。

但这种便利也有代价：在那些不希望使用该对象的地方，获取它也变得同样容易。

一般原则是：在仍然能够完成工作的前提下，变量的作用域应该尽可能小。一个对象的作用域越小，使用它时需要同时在脑中考虑的地方就越少。

在使用全局作用域的单例这种“霰弹枪式”方案之前，先看看代码库还能通过哪些方式获得对象。

#### 将它作为参数传入

最简单，而且往往也是最好的解决方案，就是将所需对象作为参数传给需要它的函数。在因为它太烦琐而放弃之前，值得先认真考虑一下。

有人将这种方式称为“依赖注入”。代码不再主动访问某个全局对象来寻找依赖，而是通过参数把依赖推送给需要它的代码。另一些人则只将更加复杂的依赖提供方式称为“依赖注入”。

以渲染对象的函数为例。为了完成渲染，它需要访问一个代表图形设备并维护渲染状态的对象。常见做法就是将该对象传给所有渲染函数，通常使用类似 `context` 的参数名。

另一方面，有些对象不适合出现在方法签名中。例如，处理 AI 的函数可能还需要写入日志文件，但日志记录并不是它的核心职责。在参数列表中看到 `Log` 会很奇怪，因此对于这类情况，我们需要考虑其他方案。

像日志记录这样散布在整个代码库中的功能被称为“横切关注点”（cross-cutting concern）。如何优雅地处理横切关注点，一直是架构设计中的难题，在静态类型语言中尤其如此。

面向切面编程（Aspect-Oriented Programming）正是为了处理这些问题而设计的。

#### 从基类中获取

许多游戏架构拥有扁平而宽广的继承层次结构，通常只有一层深度。例如，可能有一个基础 `GameObject` 类，并为游戏中的每种敌人或对象创建派生类。

在这种架构中，大量游戏代码会位于这些“叶子”派生类中。这意味着所有这些类都已经可以访问同一个东西：它们的 `GameObject` 基类。我们可以利用这一点：

```cpp
// Some code
class GameObject
{
protected:
  Log& getLog() { return log_; }

private:
  static Log& log_;
};

class Enemy : public GameObject
{
  void doSomething()
  {
    getLog().write("I can log!");
  }
};
```

这样可以确保 `GameObject` 之外的代码无法访问其 `Log` 对象，但每个派生实体都可以通过 `getLog()` 使用它。

这种让派生对象通过基类提供的受保护方法实现自身功能的模式，会在“子类沙箱”（Subclass Sandbox）一章中介绍。

这又带来了一个问题：“`GameObject` 如何获得 `Log` 实例？”

一种简单方案是，让基类直接创建并拥有一个静态实例。

如果不希望基类扮演如此主动的角色，可以提供一个初始化函数将实例传入，或者使用服务定位器模式寻找它。

#### 从已经存在的全局对象中获取

移除所有全局状态是一个值得赞赏的目标，但很少具有现实可行性。大多数代码库仍然会保留少数全局可用的对象，例如代表整个游戏状态的唯一 `Game` 或 `World` 对象。

我们可以借助这些现有的全局对象，减少全局类的数量。不要把 `Log`、`FileSystem` 和 `AudioPlayer` 都变成单例，而是这样做：

```cpp
// Some code
class Game
{
public:
  static Game& instance() { return instance_; }

  // 用于设置 log_ 等字段的函数……

  Log&         getLog()         { return *log_; }
  FileSystem&  getFileSystem()  { return *fileSystem_; }
  AudioPlayer& getAudioPlayer() { return *audioPlayer_; }

private:
  static Game instance_;

  Log         *log_;
  FileSystem  *fileSystem_;
  AudioPlayer *audioPlayer_;
};
```

这样，只有 `Game` 可以被全局访问。函数可以通过它访问其他系统：

```cpp
// Some code
Game::instance().getAudioPlayer().play(VERY_LOUD_BANG);
```

纯粹主义者会说这违反了迪米特法则（Law of Demeter）。而我要说，这仍然比堆出一大群单例要好。

如果以后修改架构以支持多个 `Game` 实例——也许用于流式加载或测试——`Log`、`FileSystem` 和 `AudioPlayer` 都不会受到影响，它们甚至不会察觉区别。

当然，这种方式的缺点是更多代码会与 `Game` 本身耦合。如果某个类只需要播放声音，在这个示例中，它仍然必须了解整个游戏世界，才能获得音频播放器。

我们可以使用混合方案解决这个问题。已经了解 `Game` 的代码可以直接从中访问 `AudioPlayer`；不了解 `Game` 的代码，则通过这里介绍的其他方式访问 `AudioPlayer`。

#### 从服务定位器中获取

到目前为止，我们假定全局类是 `Game` 这样的普通具体类。另一种选择是定义一个类，其唯一存在目的就是提供对其他对象的全局访问。

这种常见模式称为服务定位器（Service Locator），本书有专门的一章介绍它。

### 单例还剩下什么用途？

问题依然存在：我们究竟应该在哪里使用真正的单例模式？

老实说，我从未在游戏中使用过“四人帮”所描述的完整实现。为了确保只有一个实例，我通常只会使用静态类。如果静态类不合适，就使用一个静态标志，在运行时检查是否只构造了该类的一个实例。

本书还有另外两章可以帮助解决这类问题：

* 子类沙箱模式让一个类的实例能够访问某些共享状态，而不必让这些状态全局可用。
* 服务定位器模式确实会让对象全局可用，但在配置该对象的方式上提供了更大的灵活性。
