# Flyweight

迷雾渐渐散去，一片雄伟的原始森林显露在眼前。无数古老的铁杉高耸于你的头顶，构成一座绿色的教堂。枝叶组成的彩绘玻璃穹顶将阳光切割成一道道金色的雾柱。在巨大的树干之间，你可以看到这片浩瀚的森林一直延伸到远方。

这种超凡脱俗的场景正是我们游戏开发者梦寐以求的，而实现这类场景往往要归功于一个名字朴实得不能再朴实的模式：低调的享元模式（Flyweight）。

### 只见树木，不见森林

我只用几句话就能描绘出一片广袤的森林，但要在实时游戏中真正实现它，则完全是另一回事。当整个屏幕都被一棵棵树木填满时，图形程序员看到的只有数以百万计的多边形——他们必须想办法每秒六十次地将这些多边形送进 GPU。

这里说的可是成千上万棵树，而每棵树都有精细的几何结构，包含数千个多边形。即使你有足够的内存来描述整片森林，为了将它渲染出来，这些数据也必须通过总线从 CPU 传输到 GPU。

每棵树都有一大堆与之相关的数据：

* 定义树干、树枝和枝叶形状的多边形网格。
* 树皮和树叶的纹理。
* 它在森林中的位置和朝向。
* 大小、色调等调节参数，让每棵树看起来各不相同。

如果用代码大致表示出来，会是这样：

```cpp
// Some code
class Tree
{
private:
  Mesh mesh_;
  Texture bark_;
  Texture leaves_;
  Vector position_;
  double height_;
  double thickness_;
  Color barkTint_;
  Color leafTint_;
};
```

这包含了大量数据，其中网格和纹理尤其庞大。由这些对象组成的整片森林，数据量实在太大，无法在一帧内全部交给 GPU。幸运的是，我们可以使用一种历史悠久的技巧来解决这个问题。

关键在于：尽管森林里可能有成千上万棵树，但它们的外观大多相似。它们很可能都使用相同的网格和纹理。这意味着在所有这些实例中，对象的大部分字段其实都是相同的。

<figure><img src="../.gitbook/assets/image (4).png" alt=""><figcaption></figcaption></figure>



我们可以将对象一分为二，显式地表示这种共享关系。首先，提取所有树木共有的数据，并将其移入一个单独的类中：

```cpp
// Some code
class TreeModel
{
private:
  Mesh mesh_;
  Texture bark_;
  Texture leaves_;
};
```

游戏只需要一个这样的对象，因为没有理由让同一份网格和纹理在内存中重复保存上千次。然后，游戏世界中的每个树木实例都持有一个指向共享 `TreeModel` 的引用。`Tree` 中剩下的则是各个实例独有的状态：

```cpp
// Some code
class Tree
{
private:
  TreeModel* model_;

  Vector position_;
  double height_;
  double thickness_;
  Color barkTint_;
  Color leafTint_;
};
```

你可以像下面这样直观地理解它：

<figure><img src="../.gitbook/assets/image (5).png" alt=""><figcaption></figcaption></figure>

这些做法很适合在主内存中存储数据，但对渲染并没有帮助。在森林显示到屏幕上之前，相关数据必须先传输到 GPU。我们需要用显卡能够理解的方式来表达这种资源共享关系。

### 成千上万的实例

为了尽量减少需要传输到 GPU 的数据量，我们希望只发送一次共享数据，也就是 `TreeModel`。然后，再分别发送每棵树独有的数据——位置、颜色和缩放。最后告诉 GPU：“使用这一个模型来渲染所有这些实例。”

幸运的是，如今的图形 API 和显卡恰好支持这种功能。具体细节比较烦琐，也超出了本书的讨论范围，不过 Direct3D 和 OpenGL 都支持一种称为“实例化渲染”（instanced rendering）的技术。

在这两种 API 中，你需要提供两组数据流。第一组是需要被重复渲染的公共数据——在我们的树木示例中，就是网格和纹理。第二组是实例列表及其参数，用于在每次绘制时改变第一组数据。只需一次绘制调用，整片森林便拔地而起。

由于这种 API 直接由显卡实现，因此享元模式可能是“四人帮”设计模式中唯一获得硬件支持的模式。

### 享元模式

现在我们已经看过一个具体示例，接下来可以了解这个模式的一般形式。正如“享元”（Flyweight，意为轻量级）这个名字所暗示的，当你需要让对象变得更加轻量时——通常是因为对象数量太多——就可以使用享元模式。

对于实例化渲染来说，问题倒不完全是这些对象占用了太多内存，而是逐一通过总线将每棵树的数据传输到 GPU 太过耗时。不过，两者的基本思路是相同的。

享元模式通过将对象的数据分成两类来解决这个问题。第一类数据并不属于某个特定的对象实例，因此可以由所有实例共享。四人帮将其称为“内在状态”（intrinsic state），而我更喜欢把它理解为“不依赖上下文”的数据。在这个示例中，就是树木的几何结构和纹理。

剩余的数据称为“外在状态”（extrinsic state），也就是每个实例独有的数据。在这里，它指的是每棵树的位置、缩放和颜色。就像前面的示例代码一样，享元模式让对象每次出现时都共享同一份内在状态，从而节省内存。

从目前看到的内容来说，这似乎只是普通的资源共享，算不上什么值得被称为“模式”的东西。部分原因在于，在这个示例中，我们能够为共享状态找到一个清晰且独立的身份：`TreeModel`。

在共享对象没有明确身份的情况下，这个模式往往没那么显而易见，也因此显得更加巧妙。在这种情况下，就好像同一个对象神奇地同时出现在多个地方。下面再来看一个例子。

### 落地生根

游戏还需要表示这些树木生长的地面。地面上可以有草地、泥土、山丘、湖泊、河流，以及任何你能想象出来的其他地形。我们将采用基于图块的方式构建地面：整个世界的表面是一张由许多小图块组成的巨大网格，每个图块都覆盖着一种地形。

每种地形都有一些会影响游戏玩法的属性：

* 移动成本，用于决定玩家能够以多快的速度通过该地形。
* 标记它是否为水域，以确定船只能否通过。
* 用于渲染该地形的纹理。

因为我们这些游戏程序员对效率总是疑神疑鬼，所以绝不可能在世界中的每个图块里都保存所有这些状态。常见的做法是使用枚举来表示地形类型：

毕竟，我们已经从前面的树木示例中吸取了教训。

```cpp
// Some code
enum Terrain
{
  TERRAIN_GRASS,
  TERRAIN_HILL,
  TERRAIN_RIVER
  // 其他地形……
};
```

然后，游戏世界维护一张由这些枚举值组成的巨大网格：

```cpp
// Some code
class World
{
private:
  Terrain tiles_[WIDTH][HEIGHT];
};
```

这里使用嵌套数组来保存二维网格。在 C/C++ 中，这种方式很高效，因为所有元素都会紧密排列在一起。而在 Java 或其他由运行时管理内存的语言中，这样做实际上会得到一个由“行”组成的数组，其中每个元素都是指向对应“列数组”的引用，其内存效率可能没有你期望的那么高。

无论使用哪种语言，在实际代码中，最好都将这种实现细节隐藏在一个设计良好的二维网格数据结构之后。这里这样写只是为了保持示例简单。

为了真正获取某个图块的有用数据，我们会编写类似下面的代码：

```cpp
// Some code
int World::getMovementCost(int x, int y)
{
  switch (tiles_[x][y])
  {
    case TERRAIN_GRASS: return 1;
    case TERRAIN_HILL:  return 3;
    case TERRAIN_RIVER: return 2;
      // 其他地形……
  }
}

bool World::isWater(int x, int y)
{
  switch (tiles_[x][y])
  {
    case TERRAIN_GRASS: return false;
    case TERRAIN_HILL:  return false;
    case TERRAIN_RIVER: return true;
      // 其他地形……
  }
}
```

你会注意到，这里的所有方法都是 `const`。这并非巧合。由于同一个对象会在多个上下文中使用，如果对它进行修改，这些变化就会同时出现在多个地方。

这很可能不是你想要的结果。通过共享对象来节省内存，应当只是一种不会影响应用程序外在行为的优化。正因如此，享元对象几乎总是不可变的。

但是，我们并不想为世界中的每个图块都创建一个这样的实例。如果仔细观察这个类，就会发现其中没有任何数据与该图块所在的位置有关。用享元模式的术语来说，地形的所有状态都是“内在的”，或者说是“不依赖上下文的”。

既然如此，每种地形就没有必要存在多个实例。地面上的每一块草地图块都和其他草地图块完全相同。因此，世界不再是一张由枚举值或 `Terrain` 对象组成的网格，而是一张由指向 `Terrain` 对象的指针组成的网格：

```cpp
// Some code
class World
{
private:
  Terrain* tiles_[WIDTH][HEIGHT];

  // 其他内容……
};
```

所有使用同一种地形的图块都会指向同一个地形实例。

<figure><img src="../.gitbook/assets/image (6).png" alt=""><figcaption></figcaption></figure>

由于地形实例会在多个地方使用，如果采用动态分配，管理它们的生命周期就会稍微复杂一些。因此，我们直接把它们存储在 `World` 中：

```cpp
// Some code
class World
{
public:
  World()
  : grassTerrain_(1, false, GRASS_TEXTURE),
    hillTerrain_(3, false, HILL_TEXTURE),
    riverTerrain_(2, true, RIVER_TEXTURE)
  {}

private:
  Terrain grassTerrain_;
  Terrain hillTerrain_;
  Terrain riverTerrain_;

  // 其他内容……
};
```

然后，我们可以使用这些实例来铺设地面：

```cpp
// Some code
void World::generateTerrain()
{
  // 用草地填满地面。
  for (int x = 0; x < WIDTH; x++)
  {
    for (int y = 0; y < HEIGHT; y++)
    {
      // 随机点缀一些山丘。
      if (random(10) == 0)
      {
        tiles_[x][y] = &hillTerrain_;
      }
      else
      {
        tiles_[x][y] = &grassTerrain_;
      }
    }
  }

  // 铺设一条河流。
  int x = random(WIDTH);
  for (int y = 0; y < HEIGHT; y++)
  {
    tiles_[x][y] = &riverTerrain_;
  }
}
```

我承认，这算不上世界上最出色的程序化地形生成算法。

现在，我们不再通过 `World` 中的方法访问地形属性，而是直接公开 `Terrain` 对象：

```cpp
// Some code
const Terrain& World::getTile(int x, int y) const
{
  return *tiles_[x][y];
}
```

这样一来，`World` 就不再与地形的各种细节耦合。如果想获取某个图块的属性，可以直接从该对象中取得：

```cpp
// Some code
int cost = world.getTile(2, 3).getMovementCost();
```

我们又可以通过舒适自然的 API 来操作真正的对象，而且几乎没有额外开销——一个指针通常不会比一个枚举值占用更多空间。

### 性能怎么样？

我在这里说“几乎”，是因为那些斤斤计较性能的人肯定会合理地追问：这种方式与使用枚举相比，性能如何？

通过指针引用地形意味着需要进行一次间接寻址。要获取移动成本这样的地形数据，首先必须沿着网格中的指针找到地形对象，然后再从对象中找到移动成本。像这样追踪指针可能导致缓存未命中，从而降低运行速度。

关于指针追踪和缓存未命中的更多内容，请参阅“数据局部性”一章。

一如既往，优化的黄金法则是：先进行性能分析。现代计算机硬件实在太复杂，性能问题已经无法仅凭推理来判断了。在我为本章进行的测试中，使用享元对象并不比使用枚举更慢。事实上，享元对象反而明显更快。不过，这完全取决于其他数据在内存中的布局方式。

我可以确定的是，不应该不假思索地排斥享元对象。它既能带来面向对象编程风格的优点，又不需要承担大量对象产生的开销。如果你发现自己正在创建一个枚举，并围绕它编写大量 `switch` 语句，不妨考虑使用享元模式。如果担心性能问题，至少应该先进行性能分析，再决定是否将代码改成可维护性较差的形式。

### 另请参阅

在图块示例中，我们预先为每种地形创建了一个实例，并将它们存储在 `World` 中。这样就能轻松找到并复用这些共享实例。不过在很多情况下，你并不希望一开始就创建所有享元对象。

如果无法预知实际需要哪些享元对象，最好按需创建。为了获得共享带来的好处，每当请求一个对象时，首先检查是否已经创建了一个与之相同的对象。如果存在，就直接返回那个实例。

这通常意味着，你需要将对象的构造过程封装在某个接口之后，让该接口先查找是否已经存在相应的对象。像这样隐藏构造函数，正是工厂方法模式（Factory Method）的一种应用。

为了能够返回先前创建的享元对象，你还需要记录所有已经实例化的对象。顾名思义，对象池（Object Pool）可能是存放它们的合适场所。

使用状态模式（State）时，通常会有一些“状态”对象，它们不包含任何与使用该状态的状态机实例相关的字段。仅凭状态对象的身份和方法，它们就已经足够有用。在这种情况下，你可以应用享元模式，让多个状态机同时复用同一个状态实例，而不会产生任何问题。
