# Prototype

我第一次听到“原型”（prototype）这个词，是在《设计模式》中。如今，似乎每个人都在谈论“原型”，但后来我发现，他们说的并不是那个设计模式。本章会介绍原型设计模式，也会带你看看“原型”这个词及其背后的概念还出现在哪些更有趣的地方。不过，首先让我们重温一下最初的模式。

我在这里使用“最初”这个词并非随口一说。《设计模式》将 Ivan Sutherland 于 1963 年开发的传奇项目 Sketchpad，列为原型模式最早的实际应用之一。当其他人都在听 Bob Dylan 和披头士乐队时，Sutherland 正忙着——怎么说呢——发明 CAD、交互式图形和面向对象编程的基本概念。

去看看那段演示视频，准备好大吃一惊吧。

### 原型设计模式

假设我们正在制作一款《Gauntlet》风格的游戏。各种生物和恶魔成群结队地围攻英雄，争抢着从他身上分一块肉。这些令人反胃的食客通过“生成器”（spawner）进入竞技场，而每种敌人都有各自对应的生成器。

为了便于举例，假设游戏中的每种怪物都有不同的类，例如 `Ghost`、`Demon` 和 `Sorcerer`：

```cpp
// Some code
class Monster
{
  // 其他内容……
};

class Ghost : public Monster {};
class Demon : public Monster {};
class Sorcerer : public Monster {};
```

每个生成器负责构造某一种特定怪物类型的实例。为了支持游戏中的所有怪物，我们可以采用简单粗暴的方式：为每个怪物类分别创建一个生成器类，从而形成一套与怪物类相互平行的类层次结构：

<figure><img src="../.gitbook/assets/image (10).png" alt=""><figcaption></figcaption></figure>

具体实现大致如下：

```c++
// Some code
class Spawner
{
public:
  virtual ~Spawner() {}
  virtual Monster* spawnMonster() = 0;
};

class GhostSpawner : public Spawner
{
public:
  virtual Monster* spawnMonster()
  {
    return new Ghost();
  }
};

class DemonSpawner : public Spawner
{
public:
  virtual Monster* spawnMonster()
  {
    return new Demon();
  }
};

// 你应该明白这种思路了……
```

除非你的薪水是按代码行数计算的，否则这种实现方式显然不会让人愉快。大量的类、大量的样板代码、大量的冗余、大量的重复，以及大量对同一件事的反复描述……

原型模式提供了一种解决方案。其核心思想是：一个对象可以生成与自身相似的其他对象。如果你有一只幽灵，就可以用它制造更多幽灵；如果你有一只恶魔，就可以用它制造更多恶魔。任何怪物都可以作为一个原型怪物，用来生成更多与自身相同的怪物。

为了实现这一点，我们在基类 `Monster` 中添加一个抽象的 `clone()` 方法：

```cpp
// Some code
class Monster
{
public:
  virtual ~Monster() {}
  virtual Monster* clone() = 0;

  // 其他内容……
};
```

当所有怪物都支持这种操作后，我们就不再需要为每个怪物类分别创建一个生成器类了。只需定义一个通用的生成器：

```cpp
// Some code
class Spawner
{
public:
  Spawner(Monster* prototype)
  : prototype_(prototype)
  {}

  Monster* spawnMonster()
  {
    return prototype_->clone();
  }

private:
  Monster* prototype_;
};
```

生成器内部保存着一只隐藏的怪物。它存在的唯一目的，就是充当生成器的模板，用来批量复制出更多与它相似的怪物——就像一只从不离开蜂巢的蜂后。

<figure><img src="../.gitbook/assets/image (11).png" alt=""><figcaption></figcaption></figure>

为了创建幽灵生成器，我们先创建一个作为原型的幽灵实例，然后再创建一个持有该原型的生成器：

```cpp
// Some code
Monster* ghostPrototype = new Ghost(15, 3);
Spawner* ghostSpawner = new Spawner(ghostPrototype);
```

这个模式有一个巧妙之处：它不仅会复制原型的类型，还会复制原型的状态。这意味着，只要创建合适的幽灵原型，我们就能分别得到用于生成快速幽灵、虚弱幽灵或缓慢幽灵的生成器。

我觉得这个模式既优雅又出人意料。我无法想象自己能够独立想出它，但现在了解它以后，我也无法想象自己不知道它。

### 它的效果如何？

好吧，我们不再需要为每种怪物创建单独的生成器类，这很好。但我们仍然必须在每个怪物类中实现 `clone()`，其代码量和那些生成器类其实差不了多少。

而且，当你真正尝试编写一个正确的 `clone()` 时，还会陷入一些棘手的语义泥潭。它应该执行深拷贝还是浅拷贝？换句话说，如果一只恶魔拿着一把干草叉，那么复制恶魔时是否也要复制那把干草叉？

此外，在这个刻意设计的问题中，原型模式不仅看起来没有节省多少代码，问题本身也并不自然。我们不得不预先假定每种怪物都有单独的类。如今，大多数游戏引擎显然都不会这样设计。

我们中的大多数人都通过惨痛经历认识到，这种庞大的类层次结构管理起来十分麻烦。因此，我们转而使用组件模式（Component）和类型对象模式（Type Object）等方式来表示不同种类的实体，而不是把每种实体都供奉在自己的类中。

### 生成函数

即使每种怪物确实拥有不同的类，我们也还有其他办法来给这只 `Felis catus`——也就是家猫——剥皮。我们不为每种怪物创建单独的生成器类，而是定义相应的生成函数：

```cpp
// Some code
Monster* spawnGhost()
{
  return new Ghost();
}
```

与为了构造某种怪物而创建一整个类相比，这种方式需要的样板代码更少。随后，唯一的生成器类只需保存一个函数指针：

```cpp
// Some code
typedef Monster* (*SpawnCallback)();

class Spawner
{
public:
  Spawner(SpawnCallback spawn)
  : spawn_(spawn)
  {}

  Monster* spawnMonster()
  {
    return spawn_();
  }

private:
  SpawnCallback spawn_;
};
```

要创建幽灵生成器，可以这样写：

```cpp
// Some code
Spawner* ghostSpawner = new Spawner(spawnGhost);
```

### 模板

如今，大多数 C++ 开发者都已经熟悉模板。我们的生成器类需要构造某种类型的实例，但又不希望把某个特定怪物类硬编码进去。自然的解决方案就是将类型本身作为参数，而模板正好允许我们这样做。

我不确定 C++ 程序员究竟是学会了热爱模板，还是模板把那些不喜欢它的人彻底吓出了 C++ 世界。无论如何，如今我看到的每个 C++ 使用者也都在使用模板。

```cpp
// Some code
class Spawner
{
public:
  virtual ~Spawner() {}
  virtual Monster* spawnMonster() = 0;
};

template <class T>
class SpawnerFor : public Spawner
{
public:
  virtual Monster* spawnMonster() { return new T(); }
};
```

使用方式如下：

```cpp
// Some code
Spawner* ghostSpawner = new SpawnerFor<Ghost>();
```

这里之所以保留 `Spawner` 类，是为了让那些不关心生成器会创建哪种怪物的代码，可以统一使用生成器，并通过 `Monster` 指针操作生成的对象。

如果只有 `SpawnerFor<T>` 类，那么这个模板的各种实例化类型之间就不存在共同的父类型。这样一来，任何需要处理任意怪物生成器的代码，本身也必须接受一个模板参数。

### 第一类类型

前面两种方案都在解决同一个需求：让 `Spawner` 类能够由某个类型进行参数化。在 C++ 中，类型通常不是第一类对象，因此需要使用一些迂回手段。如果使用 JavaScript、Python 或 Ruby 这类动态类型语言，类本身就是可以传递的普通对象，那么就能以更加直接的方式解决这个问题。

从某种意义上说，类型对象模式也是针对缺少第一类类型的一种变通方案。不过，即使语言支持第一类类型，这个模式仍然可能有用，因为它允许你自行定义“类型”究竟是什么。你可能需要与语言内置类不同的语义。

创建生成器时，只需把它应该构造的怪物类传进去——也就是那个在运行时代表怪物类型的实际对象。简直轻而易举。

有这么多可选方案，老实说，我还没有遇到过让我觉得原型设计模式是最佳答案的场景。也许你的经验有所不同，不过现在我们先把它收起来，转而讨论另一个话题：作为语言范式的原型。

### 原型语言范式

许多人认为“面向对象编程”就等同于“类”。人们对 OOP 的定义往往像互相对立的宗教派别所宣扬的信条，不过有一种争议相对较小的理解：OOP 允许你定义将数据和代码捆绑在一起的“对象”。

与 C 这样的结构化语言和 Scheme 这样的函数式语言相比，OOP 的定义性特征是将状态和行为紧密结合在一起。

你可能认为类是实现这一点唯一的方式，但包括 Dave Ungar 和 Randall Smith 在内的一群人并不同意。他们在 20 世纪 80 年代创造了一门名为 Self 的语言。它完全是一门面向对象语言，却没有类。

#### Self

从纯粹意义上说，Self 比基于类的语言更加面向对象。我们认为 OOP 将状态与行为结合起来，但实际上，使用类的语言仍然在两者之间划出了一条分界线。

想想你最喜欢的基于类语言所采用的语义。要访问对象的某项状态，需要查看实例自身的内存。也就是说，状态包含在实例中。

但要调用一个方法，就需要先查找实例所属的类，然后再从类中查找该方法。行为包含在类中。访问方法时始终存在这样一层间接关系，这意味着字段和方法本质上仍然是两种不同的东西。

<figure><img src="../.gitbook/assets/image (12).png" alt=""><figcaption></figcaption></figure>

Self 消除了这种区别。要查找任何内容，只需在对象本身中查找。一个实例可以同时包含状态和行为。你甚至可以让某个对象拥有一个完全由它独享的方法。

<figure><img src="../.gitbook/assets/image (13).png" alt=""><figcaption></figcaption></figure>

如果 Self 仅仅做到了这一点，那它用起来会非常困难。基于类的语言中的继承虽然存在缺陷，但仍然提供了一种实用机制，可以复用多态代码并避免重复。为了在没有类的情况下实现类似的能力，Self 引入了委托（delegation）。

要在某个对象中查找字段或调用方法，我们首先检查对象本身。如果对象拥有它，查找就结束了；如果没有，就继续查找该对象的父对象。父对象实际上只是指向另一个对象的引用。

当我们无法在第一个对象中找到某项属性时，就尝试在它的父对象中查找，然后是父对象的父对象，以此类推。换句话说，失败的查找会被委托给对象的父对象。

<figure><img src="../.gitbook/assets/image (14).png" alt=""><figcaption></figcaption></figure>

父对象让我们能够在多个对象之间复用行为——甚至状态——因此，我们已经获得了类的一部分功能。类的另一个关键作用，是提供一种创建实例的方式。当你需要一个新的“某某玩意”时，只需调用 `new Thingamabob()`，或者使用你偏爱的语言所采用的相应语法。类就是用于创建自身实例的工厂。

没有类时，我们该如何创建新对象？更具体地说，怎样才能创建一大批拥有共同内容的新对象？和原型设计模式一样，Self 使用的方式也是克隆。

在 Self 中，仿佛每个对象都自动支持原型设计模式。任何对象都可以被克隆。要创建一批相似的对象，可以：

1. 将一个对象塑造成你想要的样子。你可以克隆系统内置的基础 `Object`，然后往里面塞入字段和方法。
2. 克隆这个对象，想要多少个……呃……克隆体，就创建多少个。

这样，我们既获得了原型设计模式的优雅，又无须忍受亲自实现 `clone()` 的烦琐，因为克隆能力已经内置在系统中了。

这个系统如此优美、巧妙而简洁，以至于我一了解它，就开始创建一门基于原型的语言，以便积累更多实践经验。

我知道，从头构建一门语言并不是最高效的学习方式，但我能说什么呢？我这人多少有点古怪。如果你好奇的话，这门语言叫作 Finch。

### 结果怎么样？

我原本非常兴奋，迫不及待地想体验一门纯粹基于原型的语言。但当自己的语言真正运行起来后，我发现了一个令人不快的事实：用它编程根本没有那么有趣。

后来，我听说许多 Self 程序员也得出了相同的结论。不过，这个项目远远算不上失败。Self 的动态性非常强，因此为了让它运行得足够快，开发者不得不在虚拟机方面进行各种创新。

他们在即时编译、垃圾回收和方法分派优化方面发明的技术，正是如今让世界上许多动态类型语言快到足以支持超大型热门应用的技术——而且这些技术往往还是由同一批人实现的！

没错，这门语言本身很容易实现，但那是因为它把复杂性推给了使用者。我一开始真正使用它，就发现自己很怀念类所提供的结构。由于语言本身没有类，我最终不得不尝试在库层面重新构建这套机制。

也许这是因为我过去使用的都是基于类的语言，所以思维已经被这种范式影响了。但我猜，大多数人就是喜欢定义明确的“事物类别”。

除了基于类的语言取得了压倒性的成功之外，再看看有多少游戏拥有明确的角色职业，以及一份界限清晰的敌人、物品和技能清单，其中每种内容都带有整齐明确的标签。你很少会看到某款游戏中的每只怪物都是独一无二的雪花，例如“有点介于巨魔和哥布林之间，同时还混入了一点蛇的特征”。

原型确实是一种非常酷的范式，我也希望有更多人了解它。不过，我仍然很庆幸大多数人并不需要每天使用它来编程。我见过一些完全拥抱原型范式的代码，它们带有一种奇怪的模糊感，让我很难理清头绪。

真正以原型风格编写的代码少之又少，这一点也很能说明问题。我确实找过。

### 那 JavaScript 呢？

好吧，如果基于原型的语言这么不友好，那 JavaScript 又该怎么解释？这是一门使用原型的语言，每天都有数百万人在使用它。地球上运行 JavaScript 的计算机比运行其他任何语言的都多。

JavaScript 的创造者 Brendan Eich 直接从 Self 中获得了灵感，JavaScript 的许多语义也都基于原型。每个对象都可以拥有任意一组属性，包括字段和“方法”——实际上，方法只不过是存储在字段中的函数。一个对象还可以拥有另一个称为其“原型”的对象；当字段访问失败时，它会把查找委托给该原型。

从语言设计者的角度来看，原型的一个诱人之处在于，它比类更容易实现。Eich 充分利用了这一点：JavaScript 的第一个版本只用了十天就创建出来了。

尽管如此，我认为在实际使用中，JavaScript 与基于类的语言之间的共同点，要多于它与原型语言之间的共同点。有一个迹象表明 JavaScript 已经偏离了 Self：基于原型语言的核心操作——克隆——在 JavaScript 中完全不见踪影。

JavaScript 没有用于克隆对象的方法。最接近的是 `Object.create()`，它允许你创建一个会将操作委托给现有对象的新对象。即便是这个方法，也直到 ECMAScript 5 才被加入，那已经是 JavaScript 问世十四年之后了。

JavaScript 通常不使用克隆。下面看看在 JavaScript 中定义类型和创建对象的典型方式。首先定义一个构造函数：

```cpp
// Some code
function Weapon(range, damage) {
  this.range = range;
  this.damage = damage;
}
```

它会创建一个新对象并初始化其字段。调用方式如下：

```cpp
// Some code
var sword = new Weapon(10, 16);
```

这里的 `new` 会调用 `Weapon()` 函数体，并将其中的 `this` 绑定到一个新的空对象。函数体向这个对象添加一组字段，然后自动返回这个已经填充完毕的对象。

`new` 还会做另一件事。创建空对象时，它会将该对象设置为把操作委托给一个原型对象。你可以通过 `Weapon.prototype` 直接访问这个原型对象。

状态是在构造函数体中添加的，而定义行为时，通常会将方法添加到原型对象中。例如：

```cpp
// Some code
Weapon.prototype.attack = function(target) {
  if (distanceTo(target) > this.range) {
    console.log("超出攻击范围！");
  } else {
    target.health -= this.damage;
  }
}
```

这段代码向武器的原型添加了一个 `attack` 属性，其值是一个函数。由于 `new Weapon()` 返回的每个对象都会委托给 `Weapon.prototype`，现在你便可以调用 `sword.attack()`，它将执行这个函数。

整体关系大致如下：

<figure><img src="../.gitbook/assets/image (15).png" alt=""><figcaption></figcaption></figure>

让我们总结一下：

* 创建对象的方式是执行 `new` 操作，而调用它时使用的是一个代表类型的对象——构造函数。
* 状态保存在实例本身中。
* 行为需要经过一层间接访问——委托给原型——并保存在一个独立对象中。这个对象代表某种类型的所有实例所共享的方法集合。

你可以说我疯了，但这听起来非常像我之前对类的描述。你确实可以在 JavaScript 中编写原型风格的代码——只不过没有克隆——但这门语言的语法和惯用写法都在鼓励基于类的编程方式。

就我个人而言，我认为这是件好事。正如之前所说，我觉得彻底押注原型会让代码更难处理，因此我很喜欢 JavaScript 将底层的原型语义包装成一种更有“类”范儿的形式。

### 使用原型进行数据建模

好吧，我一直在讨论自己不喜欢用原型做什么，弄得这一章越来越令人沮丧。我认为这本书更接近喜剧而不是悲剧，所以最后让我们看看一个我认为原型——更准确地说是委托——确实很有用的领域。

如果统计游戏中代码与数据分别占用了多少字节，就会发现自编程诞生以来，数据所占的比例一直在稳定增长。早期游戏会通过程序化方式生成几乎所有内容，才能装进软盘和老式游戏卡带。如今，在许多游戏中，代码只是驱动游戏运行的“引擎”，游戏本身则完全由数据定义。

这很好，但把大量内容塞进数据文件，并不会神奇地解决大型项目的组织难题。事实上，它可能让问题更加棘手。我们之所以使用编程语言，正是因为它们提供了管理复杂性的工具。

我们不会把同一段代码复制并粘贴到十个地方，而是将它提取成一个可以通过名称调用的函数。我们也不会把同一个方法复制到一大堆类中，而是将它放入一个独立的类，再让其他类继承或混入它。

当游戏数据增长到一定规模时，你也会开始渴望拥有类似的功能。数据建模是一个很深的主题，我不可能在这里进行全面讲解。不过，我确实想提出一项功能，供你在自己的游戏中考虑：使用原型和委托来复用数据。

假设我们正在为前面提到的那个无耻的《Gauntlet》仿制品定义数据模型。游戏设计师需要在某种文件中指定怪物和物品的属性。

我的意思是，这是一款完全原创的游戏，其名称绝对没有受到任何既有俯视角多人地下城探索街机游戏的启发。请不要起诉我。

一种常见做法是使用 JSON。数据实体本质上就是映射、属性包，或者其他十几种称呼之一——毕竟，程序员最喜欢做的事情，莫过于为已经拥有名称的事物再发明一个新名字。

我们已经重复发明了太多次这种结构，以至于 Steve Yegge 将其称为“通用设计模式”（The Universal Design Pattern）。

游戏中的一只哥布林可能会被定义成这样：

```cpp
// Some code
{
  "name": "goblin grunt",
  "minHealth": 20,
  "maxHealth": 30,
  "resists": ["cold", "poison"],
  "weaknesses": ["fire", "light"]
}
```

这非常直观，即使是最不喜欢阅读文本的设计师也能应付。接下来，再在伟大的哥布林家族树上添加几个同辈分支：

```cpp
// Some code
{
  "name": "goblin wizard",
  "minHealth": 20,
  "maxHealth": 30,
  "resists": ["cold", "poison"],
  "weaknesses": ["fire", "light"],
  "spells": ["fire ball", "lightning bolt"]
}

{
  "name": "goblin archer",
  "minHealth": 20,
  "maxHealth": 30,
  "resists": ["cold", "poison"],
  "weaknesses": ["fire", "light"],
  "attacks": ["short bow"]
}
```

如果这是代码，我们的审美警报现在应该已经响了。这些实体之间存在大量重复，而训练有素的程序员痛恨重复。它既浪费空间，又增加编写时间。你甚至必须仔细阅读，才能确定这些数据是否真的相同。

这还是一个维护噩梦。如果决定增强游戏中的所有哥布林，就必须记得更新这三种哥布林的生命值。糟糕，糟糕，太糟糕了。

如果这是代码，我们会为“哥布林”创建一个抽象，并在三种哥布林之间复用它。但愚笨的 JSON 对这些一无所知，所以让我们把它变得聪明一点。

我们规定：如果一个对象拥有 `"prototype"` 字段，那么该字段的值就是另一个对象的名称，而当前对象会将查找委托给它。如果某项属性不存在于当前对象中，就转而到其原型中查找。

这使 `"prototype"` 成为元数据，而不是数据。哥布林有长满疣的绿色皮肤和黄色牙齿，但它们并不拥有原型。“原型”是表示哥布林的数据对象所具有的属性，而不是哥布林本身的属性。

有了这项机制，我们可以简化哥布林大军的 JSON：

```cpp
// Some code
{
  "name": "goblin grunt",
  "minHealth": 20,
  "maxHealth": 30,
  "resists": ["cold", "poison"],
  "weaknesses": ["fire", "light"]
}

{
  "name": "goblin wizard",
  "prototype": "goblin grunt",
  "spells": ["fire ball", "lightning bolt"]
}

{
  "name": "goblin archer",
  "prototype": "goblin grunt",
  "attacks": ["short bow"]
}
```

由于弓箭手和法师都将普通哥布林作为原型，因此无须在它们各自的数据中重复生命值、抗性和弱点。我们添加到数据模型中的逻辑极其简单——只是基本的单一委托——却已经消除了大量重复。

这里有一点值得注意：我们并没有设置第四个抽象的“基础哥布林”原型，让三种具体哥布林类型都委托给它。我们只是选出其中最简单的一种哥布林，然后让另外两种委托给它。

在基于原型的系统中，任何对象都可以作为克隆源，用于创建经过进一步细化的新对象，因此这种做法感觉很自然。我认为，它在这里也同样自然。它尤其适合游戏数据，因为游戏世界中经常存在一些仅此一个的特殊实体。

想想首领和独特物品。它们通常只是游戏中某种常见对象的强化版本，而原型委托非常适合用来定义它们。比如，魔法武器“斩首之剑”实际上只是一把带有额外加成的长剑，因此可以直接这样表达：

```cpp
// Some code
{
  "name": "Sword of Head-Detaching",
  "prototype": "longsword",
  "damageBonus": "20"
}
```

稍微增强游戏引擎的数据建模能力，就能让设计师更轻松地为游戏世界中的武器和怪物添加大量细微变体。而这种丰富性，正是令玩家感到愉悦的东西。

这一章是个例外。本书其他章节都在教你如何使用某种设计模式，而这一章要教你如何不要使用它。

尽管出发点是好的，“四人帮”描述的单例模式通常弊大于利。他们强调这个模式应该谨慎使用，但游戏行业在理解这条信息时，往往把它忽略了。

和任何模式一样，在不合适的地方使用单例模式，就像用夹板治疗枪伤一样有效。由于它被严重滥用，本章大部分内容都会讨论如何避免单例。不过首先，还是让我们了解一下这个模式本身。

当行业中的许多开发者从 C 转向面向对象编程时，他们遇到了一个问题：“我怎样才能获得一个实例？”他们想调用某个方法，却没有提供该方法的对象实例。单例——换句话说，将对象变成全局对象——成了一条简单的出路。
