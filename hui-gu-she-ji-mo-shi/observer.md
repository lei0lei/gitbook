# Observer

在计算机世界里，你随便扔块石头，几乎都能砸中一个采用模型—视图—控制器（MVC）架构构建的应用程序，而 MVC 的底层基础正是观察者模式。观察者模式无处不在，以至于 Java 将它放进了核心库（`java.util.Observer`），C# 更是通过 `event` 关键字将它直接融入了语言。

和软件领域的许多事物一样，MVC 是 Smalltalk 程序员在 20 世纪 70 年代发明的。Lisp 程序员大概会声称，他们早在 60 年代就想到了，只不过懒得把它写下来。

观察者模式是“四人帮”最初提出的设计模式中应用最广泛、最为人熟知的模式之一。不过，游戏开发圈有时会像修道院一样与世隔绝，所以这些内容对你来说也许都是新鲜事。如果你已经很久没有走出修道院了，就让我用一个例子来说明为什么需要这个模式。

### 成就已解锁

假设我们要为游戏添加一个成就系统。玩家完成特定目标后，可以获得数十种不同的徽章，例如“杀死 100 只猴魔”“从桥上掉下去”或者“只挥舞一只死黄鼠狼完成关卡”。

成就：黄鼠狼挥舞者

我发誓，画这张图时我完全没想到任何双关含义。

要想干净利落地实现这个系统并不容易，因为各种不同的行为都可能解锁成就。如果不小心，成就系统的触手就会蔓延到代码库的每个阴暗角落。没错，“从桥上掉下去”这个成就确实与物理引擎有关，但我们真的希望在碰撞处理算法的线性代数代码中间看到一次 `unlockFallOffBridge()` 调用吗？

这是个反问。任何有自尊的物理程序员，都不会允许我们用“游戏玩法”这种俗不可耐的东西玷污他们优美的数学代码。

和往常一样，我们希望把负责游戏某个方面的代码整齐地集中在同一个地方。问题在于，成就可能由游戏玩法的许多不同部分触发。怎样才能在不让成就代码与所有这些部分耦合的情况下实现它？

这正是观察者模式的用武之地。它允许一段代码宣布某件有趣的事情发生了，而完全不用关心谁会收到通知。

例如，我们有一段物理代码负责处理重力，并追踪哪些物体正安稳地躺在平坦表面上，哪些物体正在坠向必死的深渊。为了实现“从桥上掉下去”这个徽章，我们可以直接把成就代码塞进这里，但那会变得一团糟。我们可以改成这样：

```cpp
// Some code
void Physics::updateEntity(Entity& entity)
{
  bool wasOnSurface = entity.isOnSurface();
  entity.accelerate(GRAVITY);
  entity.update();
  if (wasOnSurface && !entity.isOnSurface())
  {
    notify(entity, EVENT_START_FALL);
  }
}
```

这段代码只是在说：“呃，我不知道有没有人在乎，不过这个东西刚刚掉下去了。至于怎么处理，你们自己看着办吧。”

物理引擎仍然必须决定要发送哪些通知，因此它并没有完全解耦。不过在架构设计中，我们通常追求的是让系统变得更好，而不是让它变得完美。

成就系统会注册自己，这样每当物理代码发出通知时，它都能收到。然后，它可以检查正在下落的物体是不是我们那位不太优雅的英雄，以及在他与经典力学发生这次令人不快的接触之前，脚下站的是不是一座桥。如果是，系统就会解锁相应的成就，并伴以烟花和号角。整个过程完全不需要物理代码参与。

事实上，我们可以修改成就列表，甚至彻底移除整个成就系统，而无须改动物理引擎中的任何一行代码。物理引擎仍会继续发送通知，浑然不觉已经没有任何东西在接收它们。

当然，如果我们永久移除了成就系统，而且再也没有其他系统监听物理引擎的通知，那么也可以顺手删掉通知代码。不过在游戏不断演进的过程中，拥有这种灵活性还是很不错的。

### 工作原理

如果你还不知道如何实现这个模式，根据前面的描述大概也能猜出来。不过为了让你更轻松，我还是快速讲解一遍。

#### 观察者

首先是那个好管闲事的类，它想知道另一个对象何时做了什么有趣的事情。这些充满好奇心的对象由以下接口定义：

```cpp
// Some code
class Observer
{
public:
  virtual ~Observer() {}
  virtual void onNotify(const Entity& entity, Event event) = 0;
};
```

`onNotify()` 的参数由你决定。这就是为什么它叫作观察者“模式”，而不是可以直接粘贴进游戏里的观察者“现成代码”。常见的参数包括发出通知的对象，以及一个通用的“数据”参数，用来塞入其他详细信息。

如果你使用的语言支持泛型或模板，那么很可能会在这里用到它们。不过，针对具体使用场景定制参数也完全没问题。在这里，我直接将参数固定为一个游戏实体，以及一个描述所发生事件的枚举值。

任何实现了这个接口的具体类都会成为观察者。在我们的例子中，观察者就是成就系统，因此代码大致如下：

```cpp
// Some code
class Achievements : public Observer
{
public:
  virtual void onNotify(const Entity& entity, Event event)
  {
    switch (event)
    {
    case EVENT_ENTITY_FELL:
      if (entity.isHero() && heroIsOnBridge_)
      {
        unlock(ACHIEVEMENT_FELL_OFF_BRIDGE);
      }
      break;

      // 处理其他事件，并更新 heroIsOnBridge_……
    }
  }

private:
  void unlock(Achievement achievement)
  {
    // 如果尚未解锁，则将其解锁……
  }

  bool heroIsOnBridge_;
};
```

#### 主题

通知方法由被观察的对象调用。按照“四人帮”的术语，这个对象称为“主题”（subject）。它有两项工作。

首先，它持有一个观察者列表，这些观察者正无比耐心地等待它传来消息：

```cpp
// Some code
class Subject
{
private:
  Observer* observers_[MAX_OBSERVERS];
  int numObservers_;
};
```

在实际代码中，你应该使用动态大小的集合，而不是这种笨拙的数组。这里坚持使用最基础的写法，是为了照顾那些来自其他语言、不了解 C++ 标准库的读者。

重要的是，主题需要公开一套用于修改该列表的公共 API：

```cpp
// Some code
class Subject
{
public:
  void addObserver(Observer* observer)
  {
    // 添加到数组中……
  }

  void removeObserver(Observer* observer)
  {
    // 从数组中移除……
  }

  // 其他内容……
};
```

这样，外部代码就能控制谁可以接收通知。主题会与观察者通信，但不会与它们产生具体耦合。在我们的例子中，物理代码里不会有任何一行提到成就系统，但它仍然能够与成就系统通信。这就是该模式的巧妙之处。

同样重要的是，主题持有的是一组观察者，而不是单个观察者。这可以确保观察者之间不会产生隐式耦合。

例如，假设音频引擎也观察坠落事件，以便播放合适的音效。如果主题只支持一个观察者，那么当音频引擎注册自己时，就会取消成就系统的注册。

这意味着两个系统会相互干扰——而且方式格外恶劣，因为后注册的系统会禁用先注册的系统。支持观察者列表可以确保每个观察者都独立于其他观察者。就它们各自所知，自己是这个世界上唯一注视着主题的东西。

主题的另一项工作是发送通知：

```cpp
// Some code
class Subject
{
protected:
  void notify(const Entity& entity, Event event)
  {
    for (int i = 0; i < numObservers_; i++)
    {
      observers_[i]->onNotify(entity, event);
    }
  }

  // 其他内容……
};
```

请注意，这段代码假设观察者不会在自己的 `onNotify()` 方法中修改观察者列表。更健壮的实现应该禁止这种并发修改，或者能够妥善处理它。

#### 可观察的物理系统

现在，只需将这些部分接入物理引擎，使它能够发送通知，并让成就系统注册自己以接收通知。我们先遵循《设计模式》中的原始做法，让 `Physics` 继承 `Subject`：

```cpp
// Some code
class Physics : public Subject
{
public:
  void updateEntity(Entity& entity);
};
```

这样，我们就能将 `Subject` 中的 `notify()` 声明为 `protected`。派生出来的物理引擎类可以调用它来发送通知，但外部代码不能调用。同时，`addObserver()` 和 `removeObserver()` 是公共方法，因此任何能够访问物理系统的对象都可以观察它。

在实际代码中，我会避免在这里使用继承。相反，我会让 `Physics` 持有一个 `Subject` 实例。观察者观察的也不再是物理引擎本身，而是一个独立的“坠落事件”对象。观察者可以通过类似下面的方式注册自己：

```cpp
// Some code
physics.entityFell()
  .addObserver(this);
```

在我看来，这就是“观察者系统”和“事件系统”的区别。使用前者时，你观察的是那个做出了有趣行为的对象；使用后者时，你观察的是一个代表“所发生的有趣事件”的对象。

现在，每当物理引擎中发生值得关注的事情时，它就会像前面的示例那样调用 `notify()`。该方法会遍历观察者列表，并通知其中的每一个观察者。

很简单，对吧？只有一个类，负责维护一组指针，这些指针指向某个接口的实例。很难相信，这么简单直接的东西竟然是无数程序和应用框架的通信骨架。

不过，观察者模式也并非没有反对者。当我询问其他游戏程序员对这个模式的看法时，他们通常会提出几种抱怨。下面来看看我们能否解决这些问题。

### “它太慢了”

我经常听到这种说法，而说这话的程序员往往并不了解该模式的具体细节。他们下意识地认为，任何带有“设计模式”气味的东西，都必然涉及一大堆类、间接调用，以及其他浪费 CPU 周期的花哨手段。

观察者模式在这方面的名声尤其糟糕，因为众所周知，它经常和一些名叫“事件”“消息”，甚至“数据绑定”的可疑家伙混在一起。其中一些系统确实可能很慢——通常是有意如此，而且有充分的理由。它们可能会进行事件排队，或者为每条通知动态分配内存。

这正是我认为记录和整理设计模式十分重要的原因。当术语的含义变得模糊时，我们也就失去了清晰、简洁地交流的能力。你说“观察者”，别人听到的却是“事件”或“消息传递”，因为要么从来没人认真写下它们之间的区别，要么对方碰巧没有读过相关内容。

这正是我试图通过本书完成的事情。为了涵盖各方面的内容，我也专门写了一章介绍事件和消息：事件队列（Event Queue）。

不过，现在你已经看过这个模式的实际实现，知道它并不是那样。发送通知只是遍历一个列表，并调用几个虚方法。诚然，这比静态分派的方法调用稍微慢一点，但除非位于对性能要求极其苛刻的代码中，否则这点开销微不足道。

无论如何，我认为这个模式最适合用在非热点代码路径中，因此通常完全能够承担动态分派的开销。除此之外，它几乎没有其他成本。我们不会为消息分配对象，也没有任何队列，只不过是一次带有间接调用的同步方法调用而已。

#### 它太快了？

事实上，正因为观察者模式是同步的，你反而需要小心。主题会直接调用观察者，这意味着只有所有观察者的通知方法都返回之后，主题才能继续执行自己的工作。一个缓慢的观察者可能会阻塞主题。

听起来很吓人，但在实践中并没有那么严重，只是需要留意这一点。长期使用这种事件驱动编程方式的 UI 程序员有一句流传已久的格言：“别阻塞 UI 线程。”

如果正在同步响应某个事件，就应该尽快完成处理并交还控制权，以免 UI 卡死。如果需要执行耗时任务，就把它交给另一个线程或工作队列。

不过，将观察者、线程和显式锁混合使用时，确实必须格外谨慎。如果观察者试图获取一个已被主题持有的锁，游戏就可能发生死锁。在高度多线程化的引擎中，使用事件队列进行异步通信可能是更好的选择。

### “它进行了太多动态内存分配”

程序员群体中的许多派别——包括大量游戏开发者——已经转向使用带垃圾回收机制的语言，动态内存分配也不像过去那样令人闻风丧胆。但对于游戏这种对性能要求很高的软件，即使使用托管语言，内存分配仍然很重要。动态分配需要时间，回收内存同样需要时间，即使这一过程是自动完成的。

许多游戏开发者担心的并不是内存分配本身，而是内存碎片。如果你的游戏必须连续运行数天而不崩溃才能通过认证，那么日益碎片化的堆内存可能会让游戏无法发布。

“对象池”一章更详细地讨论了这个问题，以及一种常见的规避方法。

在前面的示例代码中，我使用了固定大小的数组，因为我希望让代码尽可能简单。在实际实现中，观察者列表几乎总是一个动态分配的集合，会随着观察者的添加和移除而扩张或收缩。由此产生的频繁内存变动让一些人感到不安。

当然，首先要注意的是，只有在连接观察者时才会分配内存。发送通知完全不需要分配任何内存——它只是一次方法调用。如果你在游戏启动时注册好观察者，之后很少改动它们，那么内存分配量就微乎其微。

不过，如果这仍然是个问题，接下来我会介绍一种完全不进行动态内存分配，也能添加和移除观察者的实现方式。

#### 链式观察者

在目前看过的代码中，`Subject` 拥有一个指针列表，其中每个指针都指向一个正在观察它的 `Observer`。`Observer` 类本身并不持有对这个列表的引用，它只是一个纯虚接口。通常应优先使用接口，而不是包含状态的具体类，因此这总体上是件好事。

但是，如果我们愿意在 `Observer` 中加入少量状态，就可以通过让观察者对象自身串成主题的观察者列表，解决内存分配问题。主题不再持有一个独立的指针集合，而是让观察者对象成为链表中的节点：

<figure><img src="../.gitbook/assets/image (8).png" alt=""><figcaption></figcaption></figure>

为了实现这种方案，首先要移除 `Subject` 中的数组，将其替换为一个指向观察者链表头部的指针：

```cpp
// Some code
class Subject
{
  Subject()
  : head_(NULL)
  {}

  // 各种方法……
private:
  Observer* head_;
};
```

然后，为 `Observer` 添加一个指向链表中下一个观察者的指针：

```cpp
// Some code
class Observer
{
  friend class Subject;

public:
  Observer()
  : next_(NULL)
  {}

  // 其他内容……
private:
  Observer* next_;
};
```

这里还将 `Subject` 声明为友元类。主题拥有添加和移除观察者的 API，但它所管理的链表现在位于 `Observer` 类内部。让主题能够访问该链表，最简单的方法就是将其声明为友元。

注册新观察者，只需将它接入链表即可。这里选择最简单的方案，将其插入链表头部：

```cpp
// Some code
void Subject::addObserver(Observer* observer)
{
  observer->next_ = head_;
  head_ = observer;
}
```

另一种选择是将它添加到链表末尾，但这样会增加一些复杂度。`Subject` 要么必须遍历链表以找到末尾，要么需要额外维护一个始终指向最后一个节点的 `tail_` 指针。

将观察者添加到链表头部更简单，但也会产生一个副作用：当我们遍历链表并向所有观察者发送通知时，最近注册的观察者会最先收到通知。因此，如果依次注册观察者 A、B 和 C，它们接收通知的顺序将是 C、B、A。

理论上，这种顺序并不重要。良好的观察者设计应当遵循一条原则：观察同一主题的两个观察者不应存在顺序依赖。如果顺序确实很重要，就说明这两个观察者之间存在某种隐蔽的耦合，而它最终可能会反过来坑你。

接下来实现移除操作：

```cpp
// Some code
void Subject::removeObserver(Observer* observer)
{
  if (head_ == observer)
  {
    head_ = observer->next_;
    observer->next_ = NULL;
    return;
  }

  Observer* current = head_;
  while (current != NULL)
  {
    if (current->next_ == observer)
    {
      current->next_ = observer->next_;
      observer->next_ = NULL;
      return;
    }

    current = current->next_;
  }
}
```

从链表中删除节点时，通常需要像这里一样，对删除第一个节点的情况进行一些难看的特殊处理。其实还有一种更优雅的解决办法：使用指向指针的指针。

我没有在这里使用它，是因为每次展示这种写法时，至少有一半的人会感到困惑。不过，这很值得你亲自练习一下，因为它能帮助你真正建立起以指针进行思考的方式。

由于这里使用的是单向链表，所以必须遍历链表才能找到要移除的观察者。话说回来，即使使用普通数组，也同样需要进行查找。如果改用双向链表，让每个观察者同时持有指向前一个和后一个观察者的指针，就可以在常数时间内移除观察者。如果这是实际项目中的代码，我会采用这种方式。

最后只剩下发送通知了。这和遍历链表一样简单：

```cpp
// Some code
void Subject::notify(const Entity& entity, Event event)
{
  Observer* observer = head_;
  while (observer != NULL)
  {
    observer->onNotify(entity, event);
    observer = observer->next_;
  }
}
```

这里会遍历整个链表，并通知其中的每一个观察者。这可以确保所有观察者都拥有相同的优先级，并且彼此独立。

我们还可以稍微调整一下：观察者收到通知后，可以返回一个标志，指示主题应当继续遍历链表还是立即停止。如果这样做，就已经非常接近职责链模式（Chain of Responsibility）了。

还不错，对吧？一个主题可以拥有任意数量的观察者，而且完全没有动态内存分配的气息。注册和注销观察者的速度也和使用简单数组时一样快。不过，我们确实牺牲了一个小功能。

由于观察者对象本身被用作链表节点，这意味着它只能属于一个主题的观察者链表。换句话说，一个观察者同一时间只能观察一个主题。在更传统的实现中，每个主题都有自己独立的列表，因此同一个观察者可以同时存在于多个列表中。

也许你可以接受这一限制。就我的经验而言，一个主题拥有多个观察者，要比一个观察者同时观察多个主题更为常见。如果这个限制确实会带来问题，还有一种更加复杂、但仍然不需要动态内存分配的解决方案。它太长了，没法全部塞进本章，不过我可以先勾勒出大致思路，剩下的细节就留给你补充……

#### 链表节点池

和之前一样，每个主题都拥有一个观察者链表。不过，这些链表节点不再是观察者对象本身，而是一些独立的小型“链表节点”对象。每个节点都包含一个指向观察者的指针，以及一个指向链表中下一个节点的指针。

<figure><img src="../.gitbook/assets/image (9).png" alt=""><figcaption></figcaption></figure>

由于多个节点都可以指向同一个观察者，因此一个观察者可以同时出现在多个主题的列表中。这样，我们又能同时观察多个主题了。

链表有两种形式。在学校里学到的那种链表中，节点对象包含数据。而在前面的链式观察者示例中，关系正好相反：数据——这里指观察者——包含节点，也就是 `next_` 指针。

后一种形式称为“侵入式”链表（intrusive linked list），因为将对象用于链表会侵入对象本身的定义。侵入式链表的灵活性较低，但正如我们所见，它也更加高效。在 Linux 内核这类适合进行这种权衡的地方，它们很受欢迎。

避免动态内存分配的方法很简单：由于所有节点的大小和类型都相同，可以预先为它们分配一个对象池。这样，你就有了一组数量固定的链表节点，可以按需反复使用，而无须调用真正的内存分配器。

### 尚存的问题

我想，我们已经赶走了那三个被用来吓退人们、不让他们使用这个模式的妖怪。正如我们所见，它简单、快速，也能与内存管理和睦相处。但这是否意味着你应该始终使用观察者呢？

这就是另一个问题了。和所有设计模式一样，观察者模式并非包治百病。即使实现正确且高效，它也不一定是合适的解决方案。设计模式之所以名声不佳，往往是因为人们将优秀的模式用在了错误的问题上，结果反而让情况变得更糟。

目前还剩下两个挑战：一个是技术层面的，另一个更接近可维护性层面。我们先解决技术问题，因为它们通常最容易处理。

#### 销毁主题和观察者

前面介绍的示例代码相当可靠，但它回避了一个重要问题：删除主题或观察者时会发生什么？

如果你随意对某个观察者调用 `delete`，主题可能仍然持有指向它的指针。这个指针现在变成了指向已释放内存的悬空指针。当主题试图发送通知时……这么说吧，你接下来恐怕不会太愉快。

倒不是想指责谁，不过我得指出，《设计模式》完全没有提到这个问题。

销毁主题比较容易，因为在大多数实现中，观察者并不持有对主题的引用。不过，即使如此，将主题的内存送进内存管理器的回收站仍然可能造成问题。那些观察者或许还在期待未来收到通知，却不知道这种事情已经永远不会发生。严格来说，它们根本不再是观察者，只是自以为仍然是而已。

这个问题有几种解决方式。最简单的方式就是像我一样，把责任直接推给观察者：观察者被删除时，必须主动从所有主题中注销自己。多数情况下，观察者确实知道自己正在观察哪些主题，所以通常只需在析构函数中添加一次 `removeObserver()` 调用。

和许多事情一样，难点不在于怎么做，而在于能否记得去做。

如果不希望主题消亡后留下无所适从的观察者，也很容易解决。让主题在销毁前发送最后一条“临终遗言”通知即可。这样，每个观察者都能收到它，并采取自己认为适当的行动。

哀悼、送花、写挽歌，诸如此类。

人类——即使是我们这些与机器相处太久，以至于多少沾染了几分机器严谨性的人——在“始终保持可靠”这件事上依然稳定地不可靠。这正是我们发明计算机的原因：它们不会犯下我们经常犯的错误。

更安全的方案，是让观察者在被销毁时自动从所有主题中注销。如果只在观察者基类中实现一次这套逻辑，使用它的人就不必每次都记得亲自处理。

不过，这也会增加一些复杂性。每个观察者都需要维护一份自己正在观察的主题列表，最终会形成双向指针关系。

#### 别担心，我有垃圾回收器

那些使用时髦现代语言和垃圾回收器的酷孩子们，现在大概正在暗自得意。你以为自己从不显式删除任何东西，就不必担心这个问题？再想想吧！

设想一下：你有一个 UI 界面，用于显示玩家角色的各种属性，例如生命值等。玩家打开这个界面时，你为它创建一个新对象。玩家关闭界面后，你只需忘掉这个对象，让垃圾回收器负责清理。

每当角色的脸上——或者其他部位——挨了一拳，角色就会发送一条通知。UI 界面观察这个通知，并更新小小的生命条。很好。那么，当玩家关闭界面，而你没有注销观察者时，会发生什么？

UI 虽然已经不可见，却不会被垃圾回收，因为角色的观察者列表仍然持有对它的引用。每次加载这个界面，我们都会向那个越来越长的列表中添加一个新实例。

在玩家游戏、四处奔跑和战斗的整个过程中，角色会不断发送通知，而所有这些界面都会收到通知。它们虽然没有显示在屏幕上，却仍然接收通知，浪费 CPU 周期更新不可见的 UI 元素。如果它们还会播放声音之类的东西，你甚至会观察到明显错误的行为。

这个问题在通知系统中非常常见，因此还有一个专门的名字：失效监听器问题（lapsed listener problem）。由于主题会保留对监听器的引用，最终可能出现一群僵尸 UI 对象滞留在内存中。

这里的教训是：注销观察者时一定要严谨。

还有一个更能说明这个问题有多重要的证据：它甚至拥有自己的维基百科条目。

#### 到底发生了什么？

观察者模式另一个更深层的问题，正是其设计目标所带来的直接结果。我们使用它，是因为它有助于降低两段代码之间的耦合。它让主题能够与某个观察者间接通信，而无须在静态结构上与其绑定。

当你试图理解主题的行为时，这是一个真正的优势，因为任何附带的其他内容都只会造成干扰。如果正在研究物理引擎，你肯定不希望编辑器——或者自己的脑子——被一大堆成就系统的内容塞满。

另一方面，如果程序出了问题，而且缺陷跨越了某条观察者链，理解这条通信流程就会困难得多。对于显式耦合，只需查找被调用的方法即可。由于这种耦合是静态的，对普通 IDE 来说简直易如反掌。

但如果耦合是通过观察者列表建立的，那么要知道谁会收到通知，唯一的方法就是查看运行时恰好有哪些观察者位于列表中。你无法再静态分析程序的通信结构，而必须推断程序命令式、动态的运行行为。

我处理这个问题的原则非常简单：如果为了理解程序的某个部分，你经常需要同时考虑某次通信的两端，就不要使用观察者模式来表达这种联系，而应选择更加显式的方式。

开发大型程序时，你通常会把其中某些部分作为一个整体来处理。我们有很多术语来描述这一点，例如“关注点分离”“一致性与内聚性”和“模块化”，但归根结底就是：“这些东西属于一组，而另一些东西不属于这一组。”

观察者模式非常适合让这些大体上互不相关的部分相互通信，同时避免它们融合成一个庞然大物。对于专门实现单项功能或单个方面的一整块代码，它的作用则没有那么大。

这正是它非常适合前面示例的原因：成就系统和物理系统几乎是两个完全无关的领域，很可能由不同的人实现。我们希望它们之间只进行最低限度的通信，这样处理其中任何一个系统时，都不需要深入了解另一个系统。

### 当今的观察者

《设计模式》出版于 1994 年。当时，面向对象编程是最热门的范式。地球上的每个程序员都想“30 天学会 OOP”，中层管理者根据程序员创建的类的数量支付薪水，工程师则根据继承层次的深度来衡量自己的本事。

同一年，Ace of Base 乐队不只有一首，而是有三首热门单曲。这大概足以说明我们当时的品位和判断力。

观察者模式正是在这种时代氛围下流行起来的，所以它严重依赖类也不足为奇。不过，如今的主流程序员已经更加习惯函数式编程。仅仅为了接收一条通知，就必须实现一整个接口，不太符合今天的审美。

这种方式显得笨重而僵化。事实上，它确实既笨重又僵化。例如，你无法让同一个类针对不同主题使用不同的通知方法。

这就是主题通常会将自身传给观察者的原因。由于观察者只有一个 `onNotify()` 方法，如果它同时观察多个主题，就必须能够判断到底是谁调用了它。

更加现代的做法，是让“观察者”仅仅作为方法或函数的引用存在。在支持第一类函数的语言中——尤其是支持闭包的语言中——这已经成为实现观察者更常见的方式。

如今，几乎所有语言都支持闭包。C++ 克服了在没有垃圾回收机制的语言中实现闭包的难题，甚至 Java 最终也振作起来，在 JDK 8 中引入了闭包。

例如，C# 将“事件”直接融入了语言。在 C# 中，注册为观察者的是“委托”（delegate），也就是该语言中对方法引用的称呼。在 JavaScript 的事件系统中，观察者既可以是支持特殊 `EventListener` 协议的对象，也可以只是普通函数。人们几乎总是使用后一种方式。

如果今天让我设计一个观察者系统，我会采用基于函数而不是基于类的方式。即使在 C++ 中，我也更倾向于让系统支持将成员函数指针注册为观察者，而不是注册某个 `Observer` 接口的实例。

这里有一篇很有意思的博客文章，介绍了在 C++ 中实现这种方式的一种方案。

### 未来的观察者

如今，事件系统和其他类似观察者模式的机制极其常见，已经是一条被无数人走过的成熟道路。但当你用它们编写过几个大型应用程序后，就会开始注意到一件事：观察者中的大量代码最终看起来都差不多，通常无非是：

1. 收到某项状态已经改变的通知。
2. 通过命令式代码修改某部分 UI，以反映新的状态。

代码总是在做这样的事情：“哦，英雄的生命值现在是 7？那我把生命条的宽度设置成 70 像素。”

时间一长，这会变得非常乏味。长期以来，计算机科学研究者和软件工程师一直试图消除这种重复劳动。他们的尝试有许多不同的名称，例如“数据流编程”“函数式响应式编程”等。

尽管这些尝试取得过一些成功——通常局限于音频处理或芯片设计等特定领域——但我们仍然没有找到那座圣杯。与此同时，一种不那么雄心勃勃的方法开始流行起来。如今，许多较新的应用程序框架都在使用“数据绑定”。

与更加激进的模型不同，数据绑定并不试图彻底消除命令式代码，也不打算围绕一张巨大的声明式数据流图来设计整个应用程序。它所做的，是自动处理那些烦琐的重复工作：当某个值发生变化时，相应调整 UI 元素或计算属性以反映变化。

和其他声明式系统一样，数据绑定可能还是太慢、太复杂，不适合放进游戏引擎的核心。不过，如果它开始逐渐进入游戏中对性能要求没那么高的领域，例如 UI，我一点也不会感到惊讶。

与此同时，可靠的老朋友观察者模式仍会在这里等着我们。当然，它不像那些名字里同时塞进“函数式”和“响应式”的热门技术那么令人兴奋，但它极其简单，而且确实有效。

对我而言，这两点往往正是评价一个解决方案时最重要的标准。
